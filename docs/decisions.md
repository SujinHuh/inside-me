# Inside Me 결정 로그

이 문서는 제품과 기술의 결정뿐 아니라 아직 제안 또는 보류 상태인 선택지를 함께 관리한다. 결정의 결론만 남기지 않고 왜 선택했는지, 무엇을 포기했는지, 언제 다시 검토할지를 보존한다.

## 상태 정의

- `제안됨`: 선택지와 권고안이 나왔지만 사용자가 확정하지 않음
- `임시 운영`: 최종 형식은 미확정이지만 작업 연속성을 위해 되돌릴 수 있는 기본안으로 사용 중
- `확정`: 현재 적용할 결정으로 사용자가 선택했거나 명확한 요구로 지정함
- `보류`: 지금 결정하지 않기로 함
- `거절`: 검토 후 선택하지 않음
- `대체됨`: 이후 결정이 이 결정을 대신함

## DEC-003 — AI의 감정 후보 제시 방식

- 상태: 대체됨 → DEC-037
- 일자: 2026-08-18
- 관련 로그: LOG-20260818-002, LOG-20260818-003, LOG-20260818-009, LOG-20260820-002
- 관련 요구사항: REQ-001, REQ-009, REQ-026

### 맥락

사용자는 AI가 “진정한 감정”을 찾도록 돕기를 원한다. 그러나 감정은 AI가 객관적 정답처럼 확정할 수 없다.

정신건강 상태를 진단하지 않고 감정·타인의 의도를 단정하지 않는 `REQ-009` 안전 원칙은 이 결정과 별개로 적용 중이다. 여기서 미확정인 부분은 AI가 감정 후보를 몇 개, 어떤 방식으로 제시할지다.

### 선택지

1. AI가 하나의 감정을 결론으로 제시한다.
2. AI가 근거와 함께 후보를 제시하고 사용자가 선택한다.
3. AI는 질문만 하고 후보를 제시하지 않는다.

### 권고안과 이유

2번. 구체적인 도움을 제공하면서도 사용자의 자기결정권과 오류 수정 가능성을 지킨다.

### 감수하는 비용과 위험

사용자가 즉각적인 명확한 답을 기대할 때 답답하게 느낄 수 있다. 후보의 표현과 수가 적절하지 않으면 선택 피로가 생길 수 있다.

### 재검토 조건

사용자가 이 원칙을 직접 확정하거나 도그푸딩에서 후보 제시가 방해된다는 반복 신호가 나올 때.

## DEC-007 — 첫 음성 UX는 턴 방식

- 상태: 확정
- 일자: 2026-08-18
- 상태 변경 이력: LOG-20260818-003에서 제안, LOG-20260818-005에서 사용자 확정
- 관련 로그: LOG-20260818-003, LOG-20260818-005
- 관련 요구사항: REQ-002, REQ-003

### 선택지

1. 실시간 통화형 음성 대화
2. 자유 발화 → 전사 확인 → 질문 하나 → 음성/글 답변의 턴 방식
3. 최초 발화만 음성이고 이후는 글

### 결정과 이유

2번을 첫 MVP에 사용한다. 사용자는 글보다 말하면서 생각을 정리하는 방식을 선호하고, 여러 턴에 걸쳐 AI와 대화하며 감정을 차츰 구체화하기를 원한다. 전사를 확인할 수 있어 오전사를 고칠 수 있고 솔로 개발 MVP의 구현 복잡도와 비용도 낮춘다.

### 감수하는 비용과 위험

실시간 통화 같은 몰입감과 즉각성은 낮아진다.

### 재검토 조건

턴 방식 프로토타입에서 흐름이 반복적으로 끊긴다고 느낄 때.

## DEC-009 — 음성 우선, 글 입력도 함께 지원

- 상태: 확정
- 일자: 2026-08-18
- 관련 로그: LOG-20260818-005
- 관련 요구사항: REQ-002, REQ-003, REQ-012

### 맥락

사용자는 글을 쓰는 것보다 말하면서 생각을 정리하고 감정을 구체화하는 경험을 더 선호하지만 두 입력 방식을 모두 원한다.

### 결정과 이유

음성을 시작 화면의 기본 행동으로 강조하되 글 입력도 첫 버전부터 함께 제공한다. 사용자는 글보다 말하면서 생각을 정리하는 방식을 선호하지만 상황에 따라 글을 사용할 수 있기를 원한다.

### 감수하는 비용과 위험

- 두 입력 방식을 첫 MVP부터 지원하므로 음성만 구현할 때보다 입력 상태와 오류 복구가 복잡하다.
- 음성 우선 UI가 조용한 공간이나 말하기 어려운 상황의 사용자를 소외시키지 않도록 글 전환을 쉽게 유지해야 한다.

### 재검토 조건

도그푸딩에서 글 모드가 거의 사용되지 않거나, 한 흐름에서 입력 방식을 전환할 때 반복적인 오류가 생길 때.

## DEC-010 — 음성과 글이 하나의 탐색 로직을 공유

- 상태: 대체됨 → DEC-011
- 일자: 2026-08-18
- 관련 로그: LOG-20260818-005
- 관련 요구사항: REQ-002, REQ-003, REQ-012

### 맥락

사용자가 말한 “두 가지 버전”이 두 개의 독립된 화면 흐름인지, 같은 흐름의 두 입력 방식인지는 명시적으로 확정되지 않았다.

### 선택지

1. 음성과 글을 완전히 별개의 기능과 화면 흐름으로 개발한다.
2. 하나의 감정 탐색 흐름에서 음성과 글이 같은 질문 로직, 감정 후보, 결과와 저장 형식을 공유한다.

### 권고안과 이유

2번. 감정 탐색의 본질은 같고 입력 인터페이스만 다르므로 중복 개발과 두 모드 간 동작 차이를 줄인다. 어느 턴에서든 입력 방식을 전환할 수 있게 한다.

### 감수하는 비용과 위험

- 음성에 맞춘 짧은 AI 응답과 글에서 읽기 좋은 응답 길이가 달라 표현 방식을 조정해야 할 수 있다.
- 사용자가 기대한 “두 가지 버전”이 서로 다른 경험이었다면 단일 흐름이 기대를 충족하지 못할 수 있다.

### 재검토 조건

사용자가 “두 가지 버전”의 의미를 확인하거나 프로토타입에서 모드별로 다른 흐름이 필요하다고 느낄 때.

## DEC-011 — 한 앱 안에 세 가지 감정 기록 경험

- 상태: 확정
- 일자: 2026-08-18
- 관련 로그: LOG-20260818-006
- 관련 요구사항: REQ-002, REQ-003, REQ-012
- 대체한 결정: DEC-010

### 결정과 이유

한 앱 안에 다음 세 가지 경험을 둔다.

1. 먼저 자유롭게 길게 말하는 음성 기록
2. 먼저 자유롭게 작성하는 글 기록
3. AI와 음성으로 한 턴씩 주고받으며 감정을 구체화하는 대화

사용자는 말하기, 쓰기, 대화하기 중 그날 편한 방식을 선택할 수 있다.

### 감수하는 비용과 위험

- 세 진입 경험의 차이가 UI에서 명확하지 않으면 사용자가 무엇을 골라야 할지 혼란스러울 수 있다.
- 자유 음성과 글 기록이 이후 AI 질문으로 이어질 때 턴 대화와 경계가 흐려질 수 있다.
- 세 경험의 공통 로직과 개별 로직을 적절히 나누지 않으면 솔로 개발 범위가 커질 수 있다.

### 재검토 조건

각 경험의 첫 프로토타입을 사용했을 때 둘 이상의 경험이 사실상 동일하게 느껴지거나 거의 사용되지 않을 때.

- 관련 요구사항: REQ-014

### 결정과 이유

## DEC-020 — 기능 경계별로 개발 단위를 분리

### 결정과 이유

- 메인과 기록 시작

- 아주 작은 MVP에도 폴더, 인터페이스와 테스트 경계가 조금 늘어난다.
- 경계를 지나치게 잘게 나누면 기능 하나를 수정할 때 여러 파일을 오가게 된다.
- 반대로 화면에 모든 로직을 넣지 않으므로 이후 음성 공급자나 저장 방식을 바꾸기 쉽다.

### 재검토 조건

도그푸딩에서 두 모듈이 항상 함께 바뀌어 경계가 오히려 방해되거나, 새로운 기능이 현재 경계에 자연스럽게 들어가지 않을 때.

## DEC-021 — MVP 배포 구조는 모듈형 모놀리스

- 상태: 확정
- 일자: 2026-08-18
- 관련 로그: LOG-20260818-010, LOG-20260819-001
- 관련 요구사항: REQ-019, REQ-020

### 맥락

기능별 분리를 유지하면서 모놀리스와 마이크로서비스 중 어떤 배포 구조가 솔로 개발자의 일주일 MVP에 적합한지 판단해야 한다.

### 선택지

1. 기능마다 독립 서버와 배포 단위를 갖는 마이크로서비스
2. 하나의 앱과 필요할 때 하나의 얇은 API 중계만 두되 내부 코드는 기능 모듈로 나누는 모듈형 모놀리스
3. 경계 없이 화면과 외부 API 호출을 한곳에 빠르게 작성하는 단순 모놀리스

### 결정과 이유

사용자가 2번 방향을 수용했다. 한 사람이 일주일 안에 도그푸딩하려면 여러 서비스의 배포, 인증, 관측, 네트워크 실패와 데이터 일관성을 운영할 이유가 없다. 기능 모듈 경계는 유지하되 서버가 필요하면 하나의 얇은 중계로 둔다. 일기 기록은 기기에 남기고, 외부 AI 비밀 키를 보호하는 중계와 기록 동기화 서버를 구분한다.

모놀리스는 모든 코드를 한 파일이나 한 폴더에 섞는다는 뜻이 아니다. 하나의 서버 배포 단위 내부를 기능·계층별로 분리할 수 있다. 모바일 클라이언트와 서버 런타임은 서로 다른 실행 환경이므로 구분하되, 서버를 기능마다 독립 배포하는 MSA는 사용하지 않는다.

### 감수하는 비용과 위험

- 나중에 사용자가 크게 늘면 일부 기능을 독립 서비스로 떼어낼 작업이 생길 수 있다.
- 모듈 경계를 코드 리뷰와 테스트로 지키지 않으면 시간이 지나며 결합될 수 있다.
- 중계 API를 추가하면 일기 저장 서버가 없어도 네트워크와 최소 운영 비용은 생긴다.

### 재검토 조건

독립 확장이 필요한 부하, 서로 다른 보안 경계, 별도 배포 주기 또는 다수 개발팀이 실제로 생길 때.

## DEC-022 — TypeScript와 Expo 기반 범용 앱 권고

- 상태: 확정

### 맥락

안드로이드폰을 우선 사용하면서 컴퓨터에서도 쓰고, 음성 녹음과 취침 전 알림을 포함한 MVP를 빠르게 만들어야 한다. Java와 TypeScript를 포함한 구현 선택지를 비교했다.

### 선택지

1. Java 기반 네이티브 Android 앱과 별도 컴퓨터용 웹 앱
2. Kotlin과 Jetpack Compose 기반 네이티브 Android 앱과 별도 컴퓨터용 웹 앱
3. TypeScript, React Native, Expo와 Expo Router로 Android와 웹을 함께 구현
4. TypeScript 웹 앱을 먼저 만들고 Capacitor로 Android를 포장

### 권고안과 이유

3번을 권고한다. Expo 기본 프로젝트는 TypeScript, Android, iOS와 웹 구성을 제공하고 React Native for Web을 통해 공통 UI와 로직을 재사용할 수 있다. `expo-audio`는 Android와 웹에서 녹음을 지원하고, `expo-notifications`는 Android에서 서버 없이 반복 로컬 알림을 예약할 수 있어 현재 요구와 맞는다.

Java는 안드로이드 전용이라 컴퓨터용 화면을 별도로 만들어야 한다. 네이티브 Android를 선택해야 한다면 현대 Android UI 툴킷이 Kotlin 기반이므로 Java보다 Kotlin을 우선 비교하는 편이 타당하다. Capacitor는 웹 CSS 중심의 화면에 유리하지만 이번 앱은 Android 음성·알림 경험이 핵심이므로 Expo를 첫 권고로 둔다.

앱 내부에는 `EntryRepository`, `Recorder`, `Transcriber`, `ConversationAI`, `SpeechPlayer`, `Reminder` 같은 경계를 두어 플랫폼과 공급자 구현을 교체할 수 있게 한다. 외부 AI 키가 필요하면 클라이언트에 넣지 않고 TypeScript 기반의 얇은 중계 API를 별도 패키지로 추가한다.

### 감수하는 비용과 위험

- Android와 웹의 마이크 권한, 오디오 포맷, 알림과 저장 구현은 완전히 같지 않아 플랫폼별 어댑터가 필요하다.
- `expo-notifications`는 Android와 iOS 대상이므로 컴퓨터 웹 알림은 별도 구현 또는 후순위가 된다.
- Expo SQLite의 웹 지원은 현재 알파이며 추가 브라우저 보안 헤더가 필요하다. 따라서 저장 인터페이스는 공유하되 Android와 웹 저장 구현을 분리하거나 웹 범위를 줄여야 한다.
- React Native 스타일링은 일반 웹 CSS와 차이가 있어 아주 정교한 데스크톱 전용 레이아웃은 플랫폼별 보완이 필요할 수 있다.

### 재검토 조건

네이티브 Android 기능이 Expo로 막히거나, 컴퓨터 웹 경험이 Android보다 더 중요한 것으로 바뀌거나, 프로토타입에서 React Native 스타일링이 선택한 시각 방향을 구현하기 어렵다고 확인될 때.

### 진행 상태

사용자는 2026-08-19에 TypeScript를 수용한 뒤 React Native, Expo와 Expo Router까지 앞서 제안한 기술 스택으로 진행하는 것이 맞다고 확인했다. 확정된 언어 선택은 DEC-025에도 분리되어 있다.

### 재검토 조건

## DEC-027 — 하나의 저장소와 Expo 프로젝트 안에서 클라이언트·서버 경계를 분리

- 상태: 확정

- 관련 로그: LOG-20260819-001, LOG-20260820-001, LOG-20260820-002
- 관련 요구사항: REQ-019, REQ-020
- 공식 근거: [Expo monorepo 공식 문서](https://docs.expo.dev/guides/monorepos/), [Expo API Routes 공식 문서](https://docs.expo.dev/router/web/api-routes/), [Expo 환경변수 보안 안내](https://docs.expo.dev/guides/environment-variables/), [Microsoft의 모놀리스 설명](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures)

### 맥락

사용자는 모놀리식을 선택하면서도 프론트엔드와 백엔드를 별도 최상위 프로젝트로 나누어야 하는지 다시 확인하고 싶어 한다.

### 선택지

1. `frontend/`, `backend/`를 각각 독립 프로젝트로 만드는 한 저장소의 두 앱
2. 하나의 Expo 프로젝트 안에 얇은 화면 라우트, 기능 모듈, 플랫폼 연동과 비밀 키를 쓰는 서버 전용 코드를 구분
3. 클라이언트와 서버 코드를 구분하지 않고 같은 파일과 폴더에 섞음

### 결정과 이유

사용자가 권고안을 충분히 검토했는지 확인한 뒤 그대로 진행한다고 확정했다. 이번 주 MVP에는 2번을 사용한다. 저장소와 TypeScript 설정을 하나로 유지하고, 코드의 역할과 실행 경계만 분명히 한다. 외부 AI 비밀 키가 필요한 시점에만 Expo API Route 또는 동등한 서버 엔드포인트를 추가한다. 클라이언트 번들에는 비밀 키를 넣지 않는다.

확정 구조는 다음과 같다.

```text
inside-me/
├── app/                         # Expo Router의 얇은 화면·라우트
│   └── api/                     # 2단계에서 필요할 때만 추가; IMP-002에서는 생성하지 않음
├── src/
│   ├── features/                # home, calendar, text, voice, guided
│   ├── core/                    # 감정 탐색과 일일 기록 규칙
│   ├── infrastructure/          # storage, audio, ai, notifications
│   ├── navigation/              # 화면 사이 이동 계약
│   ├── platform/                # 파일 등 운영체제 연동
│   └── testing/                 # 공통 가짜 구현과 합성 fixture
├── server/                      # 2단계에서 필요할 때만 추가; IMP-002에서는 생성하지 않음
├── docs/
└── package.json
```

Expo 공식 문서는 여러 앱·패키지가 실제로 필요하면 monorepo와 workspaces를 지원하지만 설정 복잡도가 늘어난다고 명시한다. 지금은 별도 `apps/`와 `packages/` workspaces를 만들지 않고, 중계 서버가 독립 성장할 때 `apps/api`로 추출한다.

### 감수하는 비용과 위험

- 한 Expo 프로젝트의 API Routes를 사용하면 해당 배포 방식에 대한 의존성이 생길 수 있다.
- 서버 코드가 클라이언트에서 import되지 않도록 정적 검사와 리뷰가 필요하다.
- 나중에 서버가 커지면 별도 패키지로 이동하는 작업이 생긴다.

### 재검토 조건

서버 엔드포인트가 늘고 독립 테스트·배포·런타임이 필요해지거나, Expo API Routes가 선택한 AI·음성 처리에 맞지 않을 때.

## DEC-028 — 기능 경계는 유지하고 세로 흐름을 하나씩 완성

- 상태: 확정

### 결정과 이유

사용자가 권고안을 수용하고 용어를 실제 사용 행동으로 풀어서 기록해 달라고 요청했다. 코드 구조는 기능별로 분리하되 구현은 작은 세로 흐름을 끝까지 연결해 하나씩 넓힌다. 먼저 `홈 → 글 기록 → 사용자가 감정·욕구 어휘를 직접 탐색 → 선택적 보조 후보 → 최종 확인 → 로컬 저장 → 달력과 날짜 상세`가 실제로 동작하게 한다. 그다음 같은 자기 탐색·확인·저장 핵심 흐름에 실제 AI, 자유 음성, AI 턴 대화, 음성 재생과 알림을 순서대로 붙인다.

“세로 흐름”의 사용자 행동, 저장 결과와 완료 조건은 `docs/requirements.md`와 `docs/implementation-plan.md`에 풀어서 적는다. 이 용어만으로 구현 범위를 전달하지 않는다.

달력 전체, 음성 전체, AI 전체를 각각 고립해서 완성한 뒤 마지막에 통합하면 제품의 핵심 흐름이 늦게 검증되고 통합 오류가 한꺼번에 드러난다. 반대로 모든 기능을 동시에 작성하면 실패 원인과 완료 상태를 파악하기 어렵다.

### 감수하는 비용과 위험

- 첫 세로 흐름에서는 음성·AI 턴 대화가 아직 없어 제품이 미완성처럼 보인다.
- 초기 인터페이스가 실제 공급자 연결에서 수정될 수 있다.
- 기능별 디렉터리와 세로 흐름의 공통 핵심 사이 경계를 의식적으로 지켜야 한다.

### 재검토 조건

첫 세로 흐름이 너무 얇아 핵심 가치인 AI 감정 탐색을 전혀 검증하지 못하거나 실제 공급자 제약이 데이터 모델을 크게 바꿀 때.

2. EAS 내부 배포로 APK 설치 링크를 만들어 폰에 직접 설치
3. 웹사이트를 PWA로 만들어 브라우저에서 홈 화면에 설치
4. Google Play 스토어에 정식 배포

### 결정과 이유

사용자가 QR 코드로 실행하는 방식을 선택했다. 개발 중에는 Expo Go에서 QR 코드를 찍어 Android 실제 기기에 바로 실행하고, 핵심 흐름이 안정되면 EAS 내부 배포의 APK 설치 링크로 전환한다. Play 스토어 심사는 개인 도그푸딩에 사용하지 않는다.

PWA는 브라우저에서 설치할 수 있어 사용자가 처음 생각한 경험에 가깝지만, Android 네이티브 로컬 알림과 오프라인·기기 기능 검증이 핵심인 현재 제품에서는 첫 도그푸딩 경로로 권고하지 않는다. 컴퓨터 사용 경로와 보조 접근 방식으로 이후 추가한다. Play 스토어 출시는 외부 사용자 배포 준비가 끝난 뒤로 미룬다.

### 감수하는 비용과 위험

- Expo Go는 개발 컴퓨터의 서버가 켜져 있어야 하며 지원하지 않는 네이티브 모듈이 있을 수 있다.
- 내부 APK 설치는 Android가 Play 스토어 밖 앱 설치 경고를 보여 주며 새 빌드 때 다시 설치해야 한다.
- PWA를 뒤로 미루면 첫 주에는 브라우저에서 홈 화면 설치라는 사용 경험을 검증하지 못한다.
- 내부 배포 링크를 외부에 공유하면 URL을 가진 사람이 접근할 수 있으므로 개인 범위로 관리해야 한다.

### 재검토 조건

Expo Go에서 필요한 음성·알림 기능이 막힐 때, 개발 컴퓨터 없이 더 일찍 매일 사용해야 할 때, 또는 브라우저 설치 경험이 Android 네이티브보다 우선이라는 사용자 결정이 생길 때.

### 재검토 조건

컴퓨터 웹 사용이 Android보다 중요해지거나, Expo 웹에서 핵심 음성 흐름이 충분히 동작하지 않거나, 기기 간 동기화 요구가 우선순위로 올라갈 때.

- 중단 조건을 너무 넓게 두면 자주 멈추고, 너무 좁게 두면 사용자 결정이 필요한 사항을 임의로 확정할 수 있다.

### 재검토 조건

두 문서 사이에 반복과 불일치가 자주 생기거나, 실제 개발에서 역할이 단순해져 별도 워크플로 문서가 필요하지 않게 되거나, 자동화 도구가 작업 상태와 인계를 더 정확히 관리하게 될 때.

## DEC-036 — 로컬 기록 내보내기를 저장소와 분리된 플랫폼 포트로 구현

- 상태: 제안됨
- 일자: 2026-08-19
- 관련 로그: LOG-20260819-012
- 관련 요구사항: REQ-015, REQ-019, REQ-020
- 관련 질문: Q-027

### 맥락

첫 로컬 MVP는 전체 기록 내보내기를 지원해야 하지만, 기록 직렬화와 Android 파일 생성·공유는 서로 다른 책임이다. 이를 기록 저장소 하나에 넣으면 도메인 규칙이 OS 파일 처리와 섞이고, 공유 취소나 실패 뒤 민감한 임시 파일이 남을 수 있다.

### 선택지

1. `EntryRepository`가 조회·저장·삭제와 파일 내보내기를 모두 담당
2. 버전 포함 직렬화와 OS 파일 생성·공유·정리를 서로 다른 계약으로 분리
3. 첫 MVP에서 내보내기를 제외

### 제안과 이유

2번을 제안한다. 작업자 A가 `schemaVersion`을 포함한 UTF-8 JSON 직렬화와 무결성을 담당하고, 주 에이전트가 별도 파일 포트로 cache 파일 생성·공유·정리를 연결하며, 작업자 C가 민감정보 안내와 사용자 진입 화면을 담당한다. 파일명에는 사용자 이름, 감정이나 일기 내용을 넣지 않는다.

### 장점

- 저장 규칙과 플랫폼 파일 API의 책임이 분리된다.
- 공유 성공·취소·실패 뒤 임시 파일 정리를 독립적으로 테스트할 수 있다.
- Android와 PWA가 같은 데이터 형식을 공유하면서 다른 파일 어댑터를 사용할 수 있다.

### 감수하는 비용과 위험

- 계약과 테스트 대역이 하나 더 필요하다.
- 앱 밖으로 공유된 파일의 수명은 앱이 통제할 수 없으므로 사용자 안내가 필요하다.
- JSON 형식의 사용성과 복구 가능성은 실제 프로토타입에서 검증해야 한다.

### 재검토 조건

도그푸딩에서 사람이 읽기 어렵거나 복원에 부족한 정보가 발견되는 경우, Android 공유 API가 cache 정리를 보장하지 못하는 경우, 암호화된 내보내기가 MVP에 필요해지는 경우 재검토한다.

## DEC-037 — 세 입력 방식 모두에서 사용자 자기 탐색을 AI 제안보다 먼저 제공

- 상태: 확정
- 일자: 2026-08-20
- 관련 로그: LOG-20260820-002
- 관련 요구사항: REQ-001, REQ-004, REQ-012, REQ-026
- 관련 질문: Q-016, Q-028
- 대체하는 결정: DEC-003의 AI 후보 우선 제안

### 맥락

기존 흐름은 자유 글이나 음성이 끝난 뒤 임시 탐색기 또는 AI가 감정 후보를 먼저 보여 주는 순서였다. 사용자는 자유 글, 자유 음성, AI 턴 대화 어느 방식으로 들어오더라도 AI의 해석을 먼저 받기보다 제공한 감정·욕구 목록을 직접 둘러보며 자신의 언어를 먼저 찾아보고 싶다고 요청했다.

### 선택지

1. AI가 후보를 먼저 제시하고 사용자가 선택
2. 사용자가 어휘를 먼저 탐색하고 원할 때만 AI가 보조 후보를 제안
3. AI와 사용자 선택을 한 화면에 동시에 제시

### 결정과 이유

2번을 선택한다. 세 입력 방식은 입력 과정만 다르고, 입력이 끝난 뒤에는 같은 자기 탐색 화면과 핵심 계약을 사용한다.

1. 사용자가 감정 목록을 검색·분류·스크롤하며 먼저 선택하거나 직접 추가한다.
2. 욕구 목록을 주제별로 둘러보고 자신에게 중요했던 항목을 선택한다.
3. 사용자가 원하면 AI가 이야기와 자기 선택을 바탕으로 추가 후보와 차이를 설명한다.
4. 사용자가 최종 감정·욕구와 강도를 수정·확정한다.

고정 이미지는 초기 어휘와 정보 구조의 참고자료로 보존하지만, 기본 선택 UI는 접근 가능한 구조화 텍스트로 구현한다.

### 장점

- AI의 첫 제안이 사용자의 자기 인식을 고정하는 앵커링을 줄인다.
- AI 연결 전에도 첫 로컬 MVP의 감정 탐색 가치가 작동한다.
- 세 입력 방식이 같은 감정·욕구 어휘, 선택 상태와 저장 계약을 재사용한다.
- 검색, 직접 추가, 스크린 리더와 선택 상태 표시를 지원하기 쉽다.

### 감수하는 비용과 위험

- 긴 어휘 목록이 선택 피로를 만들 수 있다.
- 감정·욕구 분류와 검색용 구조화 데이터 준비가 첫 MVP 범위에 추가된다.
- 사용자가 무엇을 골라야 할지 모를 때 AI 도움까지 한 단계 더 필요해질 수 있다.
- 욕구 충족 여부 분류가 감정의 객관적 원인이나 좋고 나쁨으로 오해되지 않게 문구를 검증해야 한다.

### 재검토 조건

Android 도그푸딩에서 목록 탐색을 반복적으로 건너뛰거나, 선택 시간이 지나치게 길거나, 사용자가 AI 도움을 항상 먼저 요청하는 경우 탐색 단계의 밀도와 진입 방식을 재검토한다.

## DEC-038 — 모든 구현 단위 후 서브에이전트 독립 검수를 다음 구현의 필수 게이트로 사용

- 상태: 확정
- 일자: 2026-08-20
- 관련 로그: LOG-20260820-005, LOG-20260820-006
- 관련 요구사항: REQ-019, REQ-020, REQ-023
- 관련 질문: 없음

### 맥락

IMP-002A·IMP-002B의 Expo 기반은 주 에이전트가 설치, 호환성, 타입, 린트, 번들과 로컬 서버를 자동 검증했지만 서브에이전트가 구현 diff를 별도로 검수하지는 않았다. 사용자는 앞으로 하나의 구현이 끝나면 서브에이전트가 검수하고, 오류가 없을 때만 다음 구현으로 넘어가는 규칙을 지속 실행 문서에 추가하도록 요청했다.

### 선택지

1. 주 에이전트의 자동 검증만 통과하면 다음 구현으로 진행
2. 모든 구현 단위마다 구현에 참여하지 않은 서브에이전트가 독립 검수하고 오류 해소 후에만 진행
3. 크거나 위험한 변경만 주기적으로 모아 검수

### 결정과 이유

2번을 선택한다. 가장 작은 세로 조각 또는 원자 작업 ID 단위의 구현·통합·자동 검증이 끝나면 상태를 `독립 검수 대기`로 바꾸고 다음 구현을 멈춘다. 구현에 참여하지 않은 서브에이전트가 기준 SHA와 diff를 읽기 전용으로 검수한다.

서브에이전트가 확인한 오류가 있으면 주 에이전트가 수정·자동 재검증·재검수한다. 확인된 오류가 0개이고 미검증 범위와 남은 제안·위험을 기록했을 때만 현재 구현을 `완료`로 바꾸고 다음 구현으로 넘어간다. 독립 검수를 실행할 수 없는 환경에서는 주 에이전트의 자체 리뷰로 대체하지 않는다.

### 검수 범위와 통과 증거

- 요구사항·결정·사용자 행동 일치
- 정상·실패·취소·재시작과 데이터 보존
- 계층·공통 계약·플랫폼 경계
- 비밀정보·개인정보·로그·삭제·내보내기·마이그레이션 안전
- 테스트의 핵심 회귀·실패 경로 커버와 미검증 범위
- UI의 Android 화면, 키보드, 스크린 리더, 색상 외 표시와 디자인 원칙
- 기준·대상 SHA 또는 diff, 검수 관점, 발견·수정·재검수 결과

### 장점

- 구현자의 가정이 자동 검증과 자체 리뷰를 동시에 통과하는 오판을 줄인다.
- 오류가 뒤 단계에 누적되기 전에 작은 diff에서 수정할 수 있다.
- 다음 실행이 어떤 근거로 시작되었는지 SHA와 검수 결과로 재현할 수 있다.

### 감수하는 비용과 위험

- 매 구현 단위마다 검수 시간이 추가되어 순수 구현 속도는 느려질 수 있다.
- 검수 단위가 너무 크면 오류 위치가 흐려지고, 너무 작으면 검수 전환 비용이 커진다. 따라서 사용자 행동을 한 칸 앞으로 옮기는 가장 작은 완결 단위로 나눈다.
- 서브에이전트의 제안을 모두 오류로 취급하면 불필요한 재작업이 발생할 수 있으므로 근거가 있는 오류와 취향·후속 제안을 구분한다.

### 재검토 조건

초소형 변경에서 검수 전환 비용이 지속적으로 구현 비용보다 커지거나, 독립 검수 결과가 장기간 중복만 발생하거나, 에이전트를 사용할 수 없는 환경이 반복되면 검수 단위를 묶는 기준만 재검토한다. 확인된 오류 0개 전에 다음 구현을 막는 원칙은 유지한다.

## DEC-039 — 저장소의 Expo CLI 명령에서 익명 텔레메트리를 기본 비활성화

## DEC-042 — 완료한 기능 단위는 push와 PR 생성·갱신까지 지속 구현 루프에 포함

- 상태: 확정
- 일자: 2026-08-20
- 관련 로그: LOG-20260820-010
- 관련 요구사항: REQ-019, REQ-020, REQ-023
- 관련 질문: 없음

### 맥락

기존 루프는 구현·검증·독립 검수·로컬 커밋까지 진행하고 push와 PR은 매 요청에서 별도로 확인했다. 사용자는 각 기능이 끝날 때마다 push와 PR을 함께 올리고, 저장소 PR 템플릿을 실제 변경에 맞게 작성하는 과정을 지속 루프에 포함하도록 요청했다.

### 선택지

1. 기능을 완료해도 로컬 커밋에서 멈추고 매번 push·PR 요청을 다시 받음
2. 기능 완료 뒤 현재 브랜치 push만 자동 수행하고 PR은 별도 요청을 받음
3. 기능 완료·독립 검수·커밋 뒤 현재 브랜치를 push하고 같은 브랜치의 PR을 생성하거나 갱신함

### 결정과 이유

3번을 선택한다. 구현 단위의 자동 검증과 서브에이전트 독립 검수에서 확인된 오류가 0개이면 구현과 관련 문서를 기능 커밋 SHA A로 고정한다. 원장에 SHA A를 기록해 상태 문서 커밋 SHA B를 만들고 clean 상태를 확인한 뒤 현재 `inside-me` 개발 브랜치를 origin에 push한다. 같은 head 브랜치의 PR이 없으면 `main` 대상으로 만들고, 이미 있으면 중복 생성하지 않고 실제 변경·검증·미검증 범위에 맞게 갱신한다.

모든 PR은 `.github/pull_request_template.md`와 `docs/pull-request-guide.md` 형식을 따른다. `main...head` 전체 PR 범위의 모든 완료 기준·자동 검증·독립 검수가 통과하고 미완료 항목이 없을 때만 병합 가능한 PR로 표시한다. 하나라도 남으면 Draft를 유지한다. PR 병합·배포·force push는 이 결정에 포함하지 않는다.

### 장점

- 기능 완료 결과와 검증 근거가 GitHub에 바로 남아 다음 리뷰와 재개가 쉬워진다.
- 로컬에만 쌓인 커밋이 원격에 누락되는 일을 줄인다.
- 모든 기능 PR에서 개인정보·데이터 영향과 미검증 범위를 같은 형식으로 확인한다.

### 감수하는 비용과 위험

- 작은 기능마다 원격 push와 PR 갱신이 발생한다.
- 한 브랜치에서 여러 기능을 이어가면 PR 범위가 커질 수 있으므로 완료 단위가 달라지면 새 작업 브랜치를 사용한다.
- GitHub 인증·네트워크 실패가 발생하면 로컬 구현은 완료됐어도 원격 게이트에서 멈출 수 있다.

### 재검토 조건

PR 갱신이 너무 잦아 리뷰 단위가 흐려지거나, 기능마다 별도 브랜치가 더 적합하거나, 자동 원격 변경이 협업 흐름을 방해하면 브랜치·PR 단위를 조정한다. 병합·배포를 별도 승인으로 두는 경계는 유지한다.

## DEC-043 — PR 제목과 본문은 한국어로 작성

- 상태: 대체됨 → DEC-051
- 일자: 2026-08-20
- 관련 로그: LOG-20260820-011
- 관련 요구사항: 없음
- 관련 질문: 없음

### 맥락

현재 PR 본문은 한국어 템플릿을 사용하지만 제목에는 영문 Conventional Commit 접두어가 붙어 있었다. 사용자는 현재 PR 제목을 한국어로 바꾸고, 이후 PR도 제목과 본문을 한국어로 작성하도록 문서에 고정해 달라고 요청했다.

### 선택지

1. 본문만 한국어로 쓰고 제목 형식은 작성자에게 맡김
2. 제목과 본문을 한국어로 쓰되 코드 식별자·명령·파일명은 원문을 유지함
3. 코드 식별자와 명령까지 모두 한국어로 번역함

### 결정과 이유

2번을 선택한다. PR 제목에는 `feat:`, `docs:` 같은 영문 Conventional Commit 접두어를 붙이지 않고 변경 결과를 짧은 한국어 명사형으로 적는다. PR 본문도 한국어 템플릿에 맞춰 실제 변경·검증·미검증·문서 연결과 개인정보 영향을 한국어로 설명한다. 코드 식별자·명령·파일명은 정확성을 위해 원문을 유지할 수 있다.

### 장점

- 저장소의 주요 협업 문맥을 한국어로 일관되게 읽을 수 있다.
- 제목만 보고도 변경 결과를 바로 파악하기 쉽다.
- 기술 식별자를 억지로 번역해 의미가 흐려지는 일을 피한다.

### 감수하는 비용과 위험

- Conventional Commit 형식의 PR 제목을 전제로 하는 자동화가 생기면 별도 설정이 필요하다.
- 영문 라이브러리명과 명령이 본문에 일부 남을 수 있다.

### 재검토 조건

릴리스 자동화가 PR 제목의 Conventional Commit 접두어를 요구하거나 외부 협업자가 공통 영문 형식을 요구하면 제목 규칙을 다시 검토한다. 본문에서 실제 검증과 개인정보 영향을 명시하는 원칙은 유지한다.

첫 기록 흐름은 하루 한 기록, 날짜·월별 조회, 수정·삭제, 전체 내보내기와 후속 schema migration을 기기 안에서 처리해야 한다. IMP-003B2에서는 작업자 A가 실제 repository를 구현하기 전에 Expo Go에서 사용할 로컬 저장 기술과 조합 경계를 정해야 한다.

### 선택지

1. 메모리 저장소만 유지해 화면을 먼저 만들고 재시작 복원은 나중에 추가
2. 단순 key-value 저장소에 전체 기록 JSON을 넣음
3. Expo Go에 포함된 `expo-sqlite`를 네이티브 구조화 저장 기반으로 선택하고 repository port 뒤에 둠

### 제안과 이유

3번을 되돌리기 쉬운 기본안으로 적용한다. SQLite는 날짜 key의 유일성, 월별 조회, transaction과 user version 기반 migration을 표현하기 쉽고 Expo SDK 54의 Expo Go에 포함된다. `src/composition/`에서 네이티브 Provider를 연결하고 `src/infrastructure/storage/`에서 WAL·외래 키만 준비한다. 실제 기록 table, CRUD, 손상 데이터와 migration은 IMP-101에서 전체 parser와 repository contract test를 함께 적용한다.

웹 SQLite는 공식 문서상 alpha이며 WASM과 서버 header 설정이 필요하므로 이번 네이티브 선택을 PWA에 그대로 강제하지 않는다. 웹은 현재 영속 저장 없이 번들을 유지하고 6단계에서 별도 저장 adapter를 결정한다.

### 장점

- 하루 한 기록, 월별 달력 조회와 원자적 수정·삭제를 구조화된 제약으로 구현할 수 있다.
- Expo Go Android 도그푸딩과 호환되고 별도 서버·계정·외부 전송이 없다.
- core repository port가 저장 기술을 가려 이후 암호화·웹 저장 변경 범위를 줄인다.

### 감수하는 비용과 위험

- 새 네이티브 런타임 패키지와 schema migration 책임이 생긴다.
- 운영체제 app sandbox 외의 앱 계층 암호화는 아직 없으며 기기 위협 모델 확대 전에 보강해야 한다.
- 웹은 Android와 같은 저장 구현을 즉시 공유하지 못하고 PWA 단계에서 별도 검증이 필요하다.

### 재검토 조건

Android 실기기에서 Expo Go DB 초기화·복원이 불안정하거나, 기록 암호화 요구가 커지거나, PWA 우선순위가 올라가 웹 alpha 제약을 감수할 이유가 생기면 저장 adapter와 암호화 방식을 다시 검토한다. 사용자가 이 기본안을 확정하기 전까지 상태는 `제안됨`으로 유지한다.

## DEC-046 — 달력 얼굴은 대표 감정을 중심으로 표현

- 일자: 2026-08-23
- 관련 로그: LOG-20260823-005, LOG-20260823-006
- 관련 요구사항: REQ-007, REQ-008, REQ-018, REQ-027

### 맥락

월간 달력의 작은 날짜 셀은 한눈에 읽혀야 하지만, 사용자는 소수의 기분 단계보다 최대한 다양한 감정이 드러나기를 원한다. 하루에는 여러 감정이 함께 있을 수 있으므로 얼굴 하나가 하루 전체를 객관적으로 판정하는 것처럼 보여서도 안 된다.

### 선택지

1. 대표 감정: 사용자가 최종 선택한 감정 중 달력에서 먼저 기억하고 싶은 하나
2. 편안함 정도: 편안함에서 불편함까지의 단계
3. 감정 강도: 약함에서 강함까지의 단계

### 선택과 이유

사용자가 권고안을 수용해 1번으로 확정했다. 달력 얼굴은 사용자가 직접 고른 대표 감정을 빠르게 떠올리는 표식으로 사용한다. 정확한 대표 감정 이름을 날짜 셀에서 읽을 수 있게 하고, 추가 감정이 있으면 작은 보조 표시를 둔다. 날짜 상세에서는 대표 감정뿐 아니라 사용자가 확정한 모든 감정 이름과 각각의 강도를 그대로 보여준다.

표정 세트는 운영체제 이모지나 좋음·보통·나쁨 몇 단계에 의존하지 않는다. 현재 11개 감정 주제를 탐색과 시각 체계의 시작점으로 삼되, 실제 저장 단위는 `기쁨과 즐거움` 같은 넓은 주제가 아니라 `감사한`, `서운한`, `억울한`처럼 사용자가 선택한 구체적 감정이다. 목록에 없는 감정의 직접 추가도 유지한다. 편안함 정도와 강도는 얼굴의 중심 의미가 아니라 표정의 작은 변형이나 상세 정보로 보조한다.

### 장점

- 사용자가 그날을 어떤 감정으로 기억했는지 달력에서 바로 떠올릴 수 있다.
- 구체적인 감정 이름과 복수 감정을 보존해 감정을 몇 개의 기분 단계로 축약하지 않는다.
- 대표 감정, 편안함과 강도의 책임을 분리해 달력 아이콘 계약이 명확해진다.

### 감수하는 비용과 위험

- 다양한 감정을 작은 얼굴로 모두 구별하기 어려워 전용 표정 체계와 텍스트 레이블이 함께 필요하다.
- 사용자가 대표 감정 하나를 고르는 단계가 추가된다.
- 비슷한 얼굴이 생길 수 있으므로 색상만으로 구분하지 않고 이름과 형태를 함께 검증해야 한다.

### 재검토 조건

Android 달력 프로토타입에서 얼굴 간 구분이 어렵거나 대표 감정 선택이 부담스럽다는 결과가 반복되면 편안함·활력 좌표 또는 복수 감정 표시를 중심으로 다시 설계한다.

## DEC-048 — 첫 실제 AI는 OpenAI 저비용·품질 모델을 합성 평가하는 안

### 선택지

1. OpenAI Responses API에서 GPT-5.6 Luna를 비용 기준, Terra를 품질 비교로 합성 평가
2. Gemini Developer API 유료 등급에서 Gemini 3.5 Flash-Lite를 합성 평가
3. Anthropic Claude API에서 Claude Haiku 4.5를 합성 평가하고 음성 공급자는 별도 결정
4. 기본 30일 이내 안전 로그 가능성을 허용하지 않고 ZDR 승인 전까지 실제 연결 보류

### 제안과 이유

사용자 결정 전 1번을 제안한다. OpenAI는 저비용·품질 모델과 전사·음성 합성·Realtime 선택지를 같은 공식 플랫폼에서 제공하므로 후속 음성 단계에서 공급자 수를 줄일 가능성이 있다. 현재 공급자 독립 계약 뒤에 단일 어댑터를 추가할 수 있어 교체도 가능하다. Luna와 Terra 중 어느 모델도 품질 확인 전 기본으로 확정하지 않고, 합성 한국어 상황 20개 이상의 비단정성·후보 다양성·이유 자연스러움·스키마 성공률로 비교한다.

Responses API는 foreground 단발 요청과 `store: false`만 사용하고 웹 검색, 파일, 대화 상태와 background mode를 사용하지 않는다. 다만 이 설정은 애플리케이션 상태 저장을 줄이는 것이며 기본 안전 모니터링 로그 가능성까지 없애지 않으므로, 최대 30일 보존 가능성을 사용자가 명시적으로 수용해야 한다. 월간 모델 비용 상한은 1인당 요금이 아니라 첫 개인 도그푸딩 프로젝트 전체의 안전 한도로 $3를 제안한다.

### 장점

- 실제 일기 없이 합성 데이터로 한국어 품질과 계약 준수부터 비교할 수 있다.
- 저비용 모델이 충분하면 개인 도그푸딩 비용이 매우 작다.
- 서버와 공급자 어댑터 경계를 유지해 다른 공급자로 교체할 수 있다.
- 후속 전사·음성 공급자를 한 계정에서 검토할 수 있다.

### 감수하는 비용과 위험

- 일반 API 안전 모니터링 로그에 요청·응답이 최대 30일 보존될 수 있다.
- 모델의 한국어 감정 뉘앙스와 비단정성은 가격표만으로 증명되지 않는다.
- 한 공급자에 텍스트·음성을 모으면 운영은 단순하지만 공급자 집중 위험이 생긴다.
- 가격, 모델 이름, ZDR 자격과 데이터 정책은 바뀔 수 있어 연결 직전에 다시 확인해야 한다.

### 재검토 조건

사용자가 보존 가능성, 공급자 또는 비용 상한을 거부하거나 합성 평가에서 Luna·Terra가 안전·한국어 기준을 반복적으로 통과하지 못하면 2·3·4번을 다시 비교한다. 실제 음성 단계 전에는 전사·음성 합성의 한국어 품질, 음성 보존과 삭제 정책을 별도 결정한다.

사용자는 외부에서 폰으로만 접속 중인 환경 제약을 문서에 명시하고 영향 없는 다음 개발을 진행하도록 요청했다. 이에 따라 순수 계산기와 실제 호출 없는 합성 예산 예약·정산·차단까지 확정한다. 실제 공급자 호출, 계정·키·서버·외부 전송과 과금 계측은 계속 사용자 결정 대기로 둔다.

개발 순서는 텍스트, 자유 음성, 턴형 음성 핑퐁, Realtime 음성 핑퐁으로 제안한다. Realtime은 5분 매일 사용 시 오디오 기본 비용만 월 약 $2.25이며 대화 누적 입력까지 포함한 계획 범위를 $3~$5로 둔다. 기존 DEC-048의 프로젝트 전체 월 $3 제안은 첫 텍스트·자유 음성 단계의 안전 한도로 해석하고, Realtime 채택 시 별도 상한을 결정한다.

### 장점

- 정액처럼 보이는 추정 대신 실제 사용량과 공식 usage 필드로 비용을 재현할 수 있다.
- 저비용 턴형 음성과 자연스러운 Realtime의 비용·지연·품질을 같은 합성 대본으로 비교할 수 있다.
- 단일 in-flight, 요청 전 보수적 비용 예약과 잔여 예산 검사, 응답 후 즉시 중단으로 예상 밖 과금을 제한한다.

### 감수하는 비용과 위험

- 실제 계측에는 승인된 계정·키·서버와 소액 과금이 필요하다.
- 정확한 usage는 응답 뒤 확정되므로 마지막 요청이 $1 예산 목표를 소액 초과할 수 있다.
- Realtime 비용은 턴 수, 대화 길이, 캐시와 출력 길이에 따라 크게 달라질 수 있다.
- 가격이 바뀌면 단가 데이터와 추정치를 다시 검토해야 한다.

### 재검토 조건

사용자가 세 모드의 사용 시간이나 빈도를 다르게 정하거나, 합성 계측 결과가 계획 범위를 벗어나거나, 턴형 음성의 지연이 충분히 자연스러우면 Realtime 도입 순서와 상한을 다시 결정한다.

## DEC-051 — PR 제목은 영어 type과 한국어 설명을 조합

- 상태: 확정
- 일자: 2026-08-24
- 대체한 결정: DEC-043
- 관련 로그: LOG-20260824-017
- 관련 요구사항: 없음
- 관련 질문: 없음
- 근거: [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/), [GitHub Draft pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests#draft-pull-requests)

### 맥락

DEC-043은 PR 제목에서 영문 Conventional Commit 접두어를 제외하고 한국어만 사용하도록 정했다. 사용자는 변경 성격을 제목 앞에서 빠르게 구분할 수 있도록 영어 유형을 붙이고, 실제 설명은 한국어로 유지하는 방식을 조사한 뒤 적용해 달라고 요청했다.

공식 Conventional Commits 규격은 커밋 메시지에 `<type>[optional scope]: <description>` 구조를 사용하고 `feat`, `fix` 외 추가 유형을 허용한다. GitHub의 Draft는 변경 유형이 아니라 병합할 수 없는 작업 중 PR 상태다. 이 저장소는 해당 구조를 PR 제목에도 적용하되 현재 규모에 맞게 유형과 문법을 제한한다.

### 선택지

1. DEC-043을 유지해 접두어 없는 한국어 제목만 사용
2. `feat`, `fix`만 사용하고 나머지는 접두어 없이 작성
3. 8개 영어 type 중 하나와 한국어 제목을 조합하고 Draft는 GitHub 상태로 분리
4. scope와 breaking change까지 포함한 전체 Conventional Commits 문법을 PR 제목에 적용

### 결정과 이유

3번을 선택한다. PR 제목은 `type: 한국어 제목` 형식으로 쓰며 type은 `feat`, `fix`, `refactor`, `test`, `docs`, `build`, `ci`, `chore` 중 주된 목적 하나만 고른다. type은 소문자로 쓰고 scope는 사용하지 않는다. 본문은 기존처럼 한국어로 작성한다.

`feature:` 대신 공식 규격에서 쓰는 `feat:`를 사용한다. 여러 변경 유형이 포함된 PR도 제목에는 리뷰 초점과 결과를 가장 잘 설명하는 type 하나만 둔다. 본문의 변경 유형 체크박스는 실제 diff에 따라 복수 선택할 수 있다.

Draft는 type이나 제목 장식이 아니다. 작업 중 PR은 GitHub Draft 상태로 생성하고 `draft:` 또는 `[Draft]`를 제목에 넣지 않는다. 완료 기준을 충족하면 제목을 바꾸지 않고 Ready for review 상태로 전환한다.

### 장점

- PR 목록에서 기능·오류·테스트·문서 등의 주된 목적을 빠르게 구분할 수 있다.
- 제목의 실제 변경 설명은 한국어로 유지해 읽기 쉽다.
- 향후 squash merge나 changelog·라벨 자동화를 도입할 때 기계가 읽을 수 있는 기반이 생긴다.
- Draft 상태를 제목과 분리해 상태 변경 뒤 낡은 `[Draft]` 문구가 남지 않는다.

### 감수하는 비용과 위험

- 하나의 PR에 여러 성격이 섞이면 대표 type 선택에 판단이 필요하다.
- 이 규칙은 PR 제목에 적용한 저장소 규칙이며 Conventional Commits 규격 자체가 PR 제목을 강제하는 것은 아니다.
- 자동 검사 도입 전에는 작성자와 검수자가 형식을 확인해야 한다.
- `perf`, `revert`, scope와 breaking change 표기는 기본 8개 밖이므로 필요 시 규칙을 확장해야 한다.

### 재검토 조건

PR에서 대표 type을 고르기 어려운 사례가 반복되거나 릴리스 자동화가 `perf`, `revert`, scope 또는 breaking change를 요구하면 유형 집합과 문법을 재검토한다. 영어 설명 전체를 요구하는 외부 협업이 생겨도 본문 한국어 원칙과 함께 다시 결정한다.

## DEC-052 — 테스트 실패 원인을 분류하고 정상 동작을 보호

- 상태: 확정
- 일자: 2026-08-24
- 관련 로그: LOG-20260824-021, LOG-20260824-022, LOG-20260824-023
- 관련 요구사항: REQ-011
- 관련 질문: 없음
- 근거: [Microsoft 단위 테스트 모범 사례](https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-best-practices), [Google Test Behavior, Not Implementation](https://testing.googleblog.com/2013/08/testing-on-toilet-test-behavior-not.html), [Jest 29.7 Manual Mocks](https://jestjs.io/docs/29.7/manual-mocks), [Jest 29.7 Setup and Teardown](https://jestjs.io/docs/29.7/setup-teardown)

### 맥락

사용자는 테스트 코드가 통과하지 않는다는 이유로 이미 정상 동작하는 프로덕션 로직을 바꾸는 일이 없어야 한다고 확인하고, 해당 원칙이 반복 개발 지침에 충분히 문서화됐는지 점검과 보강을 요청했다. 기존 지침은 테스트 실행·데이터 격리·독립 검수는 규정했지만 실패 원인 분류와 정상 동작 보호를 명시적으로 구분하지 않았다.

### 선택지

1. 테스트 작성 중에는 이유와 관계없이 프로덕션 코드를 절대 변경하지 않는다.
2. 전체 테스트만 통과하면 프로덕션 코드와 테스트 중 어느 쪽을 변경해도 허용한다.
3. 요구사항과 공개 동작을 기준으로 코드·테스트·환경·미결정 실패를 분류하고, 확인된 결함·승인된 동작·동작 보존 리팩터링에만 프로덕션 변경을 허용한다.

### 결정과 이유

3번을 선택한다. 1번은 실제 버그 수정과 TDD를 막고, 2번은 잘못된 테스트가 정상 동작을 왜곡할 위험이 있다. 테스트는 공개 동작과 안정된 계약을 우선 검증하고, 실패하면 원인을 분류한 뒤 잘못된 쪽을 수정한다. 테스트가 잘못됐다면 프로덕션 코드를 바꾸지 않는다.

테스트 중심 PR에서 프로덕션 파일이 바뀌면 변경 분류와 근거, 보존한 동작과 회귀 검증을 본문에 기록한다. 근거 없이 핵심 공개 동작 assertion을 약화하거나 snapshot을 갱신하거나 테스트를 skip하는 행위, 테스트 전용 프로덕션 분기와 실제 데이터·외부 서비스 오염으로 초록색 결과를 만드는 방법은 금지한다. 테스트 결함 때문에 구현 세부 assertion을 교체한 경우에는 분류와 근거를 기록한다.

### 장점

- 테스트가 요구사항의 실행 가능한 설명으로 남고 내부 구현 변경에 불필요하게 깨지지 않는다.
- 실제 코드 결함과 테스트 자체의 오류를 구분해 정상 사용자 동작을 보호한다.
- 테스트만 추가하는 작업에서 의도하지 않은 프로덕션 변경을 리뷰 단계에서 빠르게 찾는다.
- 격리와 정리를 강제해 실행 순서와 외부 환경에 따른 불안정성을 줄인다.

### 감수하는 비용과 위험

- 실패 원인과 요구사항 근거를 확인하는 시간이 추가된다.
- 공개 동작과 비기능 구현 계약의 경계를 판단해야 하는 경우가 있다.
- 동작 보존 리팩터링도 영향 범위 회귀 테스트와 PR 설명이 필요하다.

### 재검토 조건

테스트 실패 분류가 반복적으로 모호하거나, 성능·보안·동시성처럼 내부 구현 제약을 공개 동작만으로 검증하기 어렵거나, snapshot·시각 회귀 도구를 본격 도입해 갱신 승인 절차가 필요해지면 세부 기준을 재검토한다.

2. Inside Me를 ChatGPT 안에서 실행되는 앱으로 별도 구성
3. 기기 또는 개인 Mac의 로컬 모델 사용
4. 독립 Inside Me 앱이 서버 경계를 통해 외부 AI API 호출

### 결정과 이유

4번을 선택한다. 사용자가 원하는 것은 독립 앱 화면 안에서 텍스트·자유 음성·음성 핑퐁 경험을 제공하는 것이며, ChatGPT 앱으로 이동하는 방식은 자동 응답과 기록 복귀를 완성하지 못한다. 기존 공급자 독립 포트·어댑터와 서버 중계 경계를 유지해 API 공급자와 모델을 교체할 수 있게 한다.

이 결정은 API 연동 방향만 확정한다. OpenAI 최종 채택, Luna·Terra 모델 선택, 최대 30일 안전 모니터링 보존 가능성, 월 비용 목표·하드 지출 한도, IMP-204C의 $1 합성 계측, 계정·키·서버 준비는 Q-013에서 별도로 승인받는다. 승인 전 실제 요청과 과금은 시작하지 않는다.

### 장점

- 사용자가 앱을 벗어나지 않고 AI 탐색을 이어 갈 수 있다.
- 텍스트·음성 입력이 같은 감정 탐색 핵심 로직과 저장 흐름을 공유할 수 있다.
- 공급자 경계를 유지해 비용·품질·개인정보 조건이 달라지면 교체할 수 있다.
- 프로젝트와 앱 양쪽의 예산 차단으로 개인 투자 범위를 통제할 수 있다.

### 감수하는 비용과 위험

- ChatGPT Pro 구독과 별개인 API 사용료와 향후 서버 운영비가 발생한다.
- 감정 기록과 음성이 외부 처리 경계를 통과하므로 명시적 동의, 최소 전송과 보존 고지가 필요하다.
- 플랫폼 지출 한도와 앱 차단 모두 반영 지연과 진행 중 요청 때문에 설정액을 소액 초과할 수 있다.
- 공급자·모델 가격과 정책이 바뀔 수 있어 연결·배포 전 재확인이 필요하다.

### 재검토 조건

합성 평가에서 한국어 감정 뉘앙스·비단정성·안전 기준을 충족하지 못하거나, 실제 개인 사용 비용이 승인 상한을 반복적으로 넘거나, 로컬 모델이 품질과 기기 요구사항을 충족하면 공급자 또는 연동 방식을 재검토한다. 독립 앱 내부 자동 대화보다 ChatGPT 수동 연결이 실제 도그푸딩에서 충분하다고 확인돼도 API 범위를 축소할 수 있다.

## DEC-054 — 제공 이미지의 전체 감정·욕구를 단계형 탐색으로 제공

- 상태: 부분 대체됨 → 전체 어휘 보존은 유지, 화면 깊이는 DEC-055로 대체
- 일자: 2026-08-24
- 관련 로그: LOG-20260824-032, LOG-20260824-033
- 관련 요구사항: REQ-004, REQ-026, REQ-027, REQ-028
- 관련 질문: Q-028
- 근거: `docs/references/2026-08-18-emotion-types.jpg`, `docs/references/2026-08-18-feelings-needs-list.jpg`

### 맥락

첫 Android 선확인에서 대표 감정 24개와 욕구 16개만 있는 카탈로그는 사용자가 처음 제공한 이미지의 다양한 표현을 찾기에 지나치게 제한적이었다. 사용자는 감정 일기의 핵심이 자신의 감정과 욕구를 구체적으로 알아가는 데 있으므로 대표 몇 개로 축약하지 않고 이미지의 표현을 웬만하면 모두 선택하고 싶다고 밝혔다.

### 선택지

1. 현재 대표 어휘를 유지하고 목록에 없으면 직접 입력
2. 대표 어휘 수만 조금 늘리고 현재 한 화면 필터 구조 유지
3. 이미지의 원문 후보를 거의 모두 구조화하고 감정의 두 탐색 관점과 욕구 8개 범주를 단계형 화면으로 제공
4. 원본 이미지 자체를 확대·축소해 단어를 찾고 별도 입력란에 옮김

### 결정과 이유

3번을 선택한다. 감정 화면의 첫 깊이에는 `욕구 충족과 연결된 느낌`과 `욕구 미충족과 연결된 느낌`을 분명히 보여 주고, 사용자가 선택한 안쪽 화면에서 해당 표현 전체를 검색·스크롤·복수 선택한다. 두 관점은 감정의 원인이나 좋고 나쁨을 판정하는 값이 아니므로 사용자는 양쪽을 자유롭게 오갈 수 있고 선택이 유지된다. `여러 느낌이 섞여 있어요`, `아직 모르겠어요`, `전체 감정 보기`와 직접 입력도 탈출 경로가 아니라 동등한 탐색 경로로 둔다.

욕구 화면의 첫 깊이에는 자율성, 신체적 안녕과 생존, 사회적·정서적 상호의존, 놀이와 재미, 삶의 의미, 진실성, 아름다움과 평화, 자기구현의 8개 큰 범주를 보여 준다. 범주를 누르면 다음 깊이에서 이미지의 세부 욕구를 검색·스크롤하고 복수 선택한다. 뒤로 이동하거나 다른 범주를 열어도 기존 선택을 유지하고 화면 하단 또는 별도 선택 요약에서 현재 선택을 확인한다.

이미지 자체를 선택 UI로 복제하지 않고 원문 후보를 안정 ID가 있는 텍스트 데이터로 옮긴다. 원문은 우선 보존하며 명백한 중복·오탈자, 감정이 아니라 평가나 생각에 가까운 표현은 원문 대조표에서 삭제하지 않고 표시·검색 별칭·설명 방식으로 검토한다. 정확한 이름 외에도 검색어를 제공하고, 목록에 없는 사용자 표현을 직접 추가할 수 있게 한다.

### 장점

- 사용자가 AI 제안 전에 자신의 경험과 가까운 구체적인 표현을 충분히 찾을 수 있다.
- 긴 목록을 한 화면에 작은 글씨로 압축하지 않으면서 원본 이미지의 구조와 다양성을 보존한다.
- 큰 범주에서 세부 표현으로 내려가므로 처음부터 전체 목록을 마주하는 선택 피로를 줄인다.
- 검색·복수 선택·접근성 상태·직접 추가와 저장 계약을 유지할 수 있다.

### 감수하는 비용과 위험

- 전체 원문 전사, 중복·오탈자 대조, 안정 ID와 검색어 작성 및 테스트 작업이 추가된다.
- 화면 깊이가 한 단계 늘어나므로 뒤로 가기와 선택 유지가 명확해야 한다.
- 충족·미충족이라는 관점이 감정의 객관적 원인이나 긍정·부정 판정으로 오해될 수 있어 안내 문구와 혼합·전체 경로가 필요하다.
- 전체 어휘가 많아 검색·스크롤 성능, 작은 화면 밀도와 스크린 리더 탐색량을 Android에서 재검증해야 한다.

### 재검토 조건

실제 도그푸딩에서 사용자가 반복적으로 범주 선택을 건너뛰거나 원하는 표현을 찾는 시간이 과도하게 길고, 검색·최근 선택·즐겨찾기 같은 더 빠른 경로가 필요하다고 확인되면 첫 화면과 목록 밀도를 재검토한다. 이미지 원문의 특정 표현이 반복해서 판단·진단처럼 받아들여지면 원문 추적을 유지한 채 표시 문구와 설명을 조정한다.

## DEC-055 — 분류를 먼저 고르지 않는 한 장 마음 지도를 기본 탐색으로 사용

- 상태: 대체됨 → DEC-064
- 일자: 2026-08-24
- 관련 로그: LOG-20260824-035, LOG-20260824-036, LOG-20260824-037
- 관련 요구사항: REQ-004, REQ-021, REQ-022, REQ-026, REQ-027, REQ-028
- 관련 질문: Q-030, Q-031
- 대체하는 결정: DEC-054의 단계형 화면 깊이

### 맥락

감정의 충족·미충족 관점이나 `여러 느낌이 섞여 있어요`를 먼저 고르는 비교안은 사용자가 단어를 보기 전에 자신의 상태를 분류하도록 요구했다. 사용자는 원본 두 이미지처럼 전체 감정과 욕구를 먼저 훑으며 단어 자체에서 마음을 알아차리고 싶다고 했고, 한 장 전체 지도형 정보 구조는 괜찮다고 확인했다. 디자인은 이후에도 바꿀 수 있으므로 실제 API 전에 시각 마감을 완전히 확정할 필요는 없다고 보았다.

### 결정과 이유

충족과 연결된 감정, 미충족과 연결된 감정, 욕구 8개 영역과 세부 욕구를 한 개의 검색·스크롤 화면에 모두 펼친 `한 장 마음 지도`를 기본 탐색으로 사용한다. 사용자는 분류를 먼저 고르지 않고 어느 영역에서든 바로 복수 선택하며, 양쪽 감정을 고르면 별도의 `섞임` 판정 없이 함께 유지한다. 상단 빠른 이동과 전체 검색은 탐색을 돕지만 목록을 제한하지 않는다.

시각 톤은 컬러 감정 지도를 도그푸딩용 임시 기본안으로 삼는다. Windows 정체성은 파란 제목 표시줄, 창 경계와 명확한 선택 상태에 남기고 회색 면과 강한 입체 음영을 모든 내부 요소에 반복하지 않는다. 소프트 윈도우도 대안으로 보존하며 실제 Android 사용 후 색, 곡률, 음영과 밀도를 바꿀 수 있다.

API 연결 전에 시각 마감 전체를 끝내지는 않지만 `IMP-107A`에서 전체 어휘의 안정 ID와 원본 대조를 먼저 고정한다. 현재 외부 AI 응답은 카탈로그 ID에 매핑되므로 대표 24개·16개 기준으로 실제 연결하면 전체 어휘 확장 뒤 계약·평가를 다시 수정해야 하기 때문이다.

### 감수하는 비용과 위험

- 한 화면이 길어져 빠른 이동, 검색, 선택 요약과 렌더링 성능이 중요하다.
- 많은 색을 사용하면 감정의 좋고 나쁨을 암시하거나 Windows 정체성이 약해질 수 있다.
- 임시 디자인으로 구현한 뒤 도그푸딩 결과에 따라 다시 다듬는 작업이 남는다.
- 전체 어휘 ID가 고정될 때까지 실제 API 매핑 구현을 시작할 수 없다.

### 재검토 조건

Android에서 전체 지도의 스크롤이 지나치게 길거나 사용자가 반복적으로 검색만 사용하고 영역을 보지 않으면 접힌 그룹, 최근 선택 또는 즐겨찾기를 검토한다. 컬러 감정 지도가 산만하거나 감정의 가치 판단처럼 느껴지면 소프트 윈도우 톤으로 조정한다.

### 대체 이력

Android UX-01과 A·B·C 목업 비교 결과, 한 장 세로 지도는 C안 `세 개의 마음 방`으로 대체됐다. 전체 271개 접근, 한 검색, 복수 선택, 분류를 정답처럼 강요하지 않는 원칙과 구조화된 전체 목록 대체 경로는 DEC-064에서도 유지한다.

## DEC-056 — 첫 실제 AI 공급자로 OpenAI API를 사용

- 상태: 확정 — 모델·보존·예산·실제 계측은 Q-013 대기
- 일자: 2026-08-25
- 관련 로그: LOG-20260825-004
- 관련 요구사항: REQ-003, REQ-009, REQ-019, REQ-020, REQ-026
- 관련 질문: Q-013

### 맥락과 결정

사용자는 Inside Me의 첫 실제 AI 연동에 OpenAI API를 사용하기로 확정했다. 현재는 외부에서 폰으로 원격 개발 중이므로 API 키를 제공하거나 실제 외부 호출을 검증할 수 없다. 따라서 이번 구현은 서버 요청·응답 계약, Responses API의 구조화 출력 요청, HTTP gateway와 이중 런타임 검증까지만 생성하고 실제 키·호출·과금·Expo 조합은 제외한다.

### 안전과 구조

- 비밀 키는 Expo 앱·`EXPO_PUBLIC_*`·Git·문서·로그에 넣지 않고 서버 실행 환경에서만 주입한다.
- 서버는 이야기와 사용자가 직접 고른 카탈로그 ID만 받고, 모델 탐색에 필요한 카탈로그 `ID + 표시 이름`만 추가한다.
- 과도한 민감 원문 전송과 비용 폭증을 막기 위해 서버에서 하나의 이야기를 UTF-8 16,000바이트로 임시 제한한다. 5분 텍스트·전사 도그푸딩에서 부족하면 사용자 경고와 요약·분할 정책을 함께 재검토한다.
- OpenAI 응답은 카탈로그 ID, 이유 코드, 종류별 최대 5개로 구조화하고 서버와 앱 경계에서 각각 검증한다.
- `store: false`를 요청하지만 이를 완전 무보존으로 표현하지 않고 공식 데이터 정책 수용 여부를 실제 호출 전 다시 결정한다.

### 감수하는 비용과 재검토 조건

- 매 요청에 전체 271개 카탈로그 이름을 포함하면 입력 토큰과 지연이 늘어날 수 있다. IMP-204C에서 실제 토큰을 계측한 뒤 캐싱·후보 축소·모델 조정을 비교한다.
- 모델은 현재 코드에 고정하지 않고 서버 구성으로 주입한다.
- 한국어 합성 평가가 안전성·비단정성·어휘 다양성 기준을 충족하지 못하거나 실제 비용이 승인 한도를 반복해 넘으면 모델 또는 공급자를 재검토한다.

## DEC-058 — 공급자 호출 뒤 비용을 알 수 없으면 보수적으로 예약액을 정산한다

### 재검토 조건

## DEC-059 — 실기기 대기 중 자유 음성의 기기 비의존 기반을 먼저 구현한다

### 맥락과 선택지

텍스트 MVP의 다음 공식 포인터는 IMP-106 Android 누적 검증이지만 사용자는 현재 외부에 있어 실기기 검증을 진행하기 어렵다. 전체 제품에는 아직 자유 음성 기록과 AI 턴 대화가 남아 있으므로, 대기 시간에 후속 기능을 안전하게 앞당길 수 있는지 검토한다.

### 재검토 조건

사용자가 텍스트 MVP 완료 전 음성 기반 선행 구현을 원하지 않거나, 실제 Android 녹음 API·전사 공급자 선택이 계약 자체를 바꾸는 것으로 확인되면 IMP-301A를 IMP-106 뒤로 되돌린다.

## DEC-060 — 전체 지도를 유지하되 모바일 첫 화면에 탐색 개요와 선택 현황을 둔다

Android 도그푸딩에서 전체 271개 어휘는 구현돼 있었지만 첫 감정 단어가 첫 화면 아래로 밀리고, 동일한 칩이 길게 반복돼 어디서 탐색을 시작할지 한눈에 파악하기 어렵다는 UX-01이 확인됐다.

- How We Feel은 먼저 색으로 구분된 Mood Meter에서 영역을 찾고 세부 감정 단어를 고르며, 검색과 사용자 감정 추가 및 두 번째 감정 선택을 제공한다. 전체 어휘를 다루면서도 첫 시작점을 시각적으로 줄이는 사례다.

- `한눈에 들어온다`는 271개를 한 뷰포트에 압축한다는 뜻이 아니다. 첫 화면에서 `충족 감정`, `미충족 감정`, `욕구`의 세 축, 욕구가 8개 영역으로 이어진다는 구조·접근 경로, 탐색 시작점과 검색·세로 스크롤로 전체 목록에 이어지는 방법을 이해한다는 뜻이다. 8개 이름을 첫 화면에 모두 둘지는 확정하지 않는다.
- QA는 정적·코드 검증, 브라우저 보조 QA, 설명 없는 사용자 첫 보기 QA, Android 실기기 QA를 서로 다른 증거로 기록한다.
- 사용자 첫 보기 QA는 정해진 질문 뒤 세 탐색 축과 욕구 8개 영역의 존재·접근 경로를 식별하고, 도움 없이 8개 영역 목록과 실제 단어에 도달하는 과업으로 판정한다. 임의의 시간 제한이나 미감 평가만으로 통과시키지 않는다.
- 외부 접근성 기준은 재배치·대비·포커스·레이블·조작 영역의 최소선으로 사용하고, 제품 목적에 맞는 첫 보기 과업을 별도 합격 기준으로 둔다.
- 이 결정은 DEC-060의 특정 목업, 소프트 파스텔 톤 또는 프로덕션 UI 구현을 승인하지 않는다. 시각 방향은 Q-034의 사용자 결정으로 남긴다.

### 장점과 감수하는 비용

- 구현 수량과 버튼 동작만 통과하고 실제 사용자가 시작하지 못하는 거짓 완료를 막는다.

- 한 명의 개인 도그푸딩 결과는 해당 버전의 근거일 뿐 외부 사용자 전체의 성공률을 보장하지 않는다.
- 사용자 첫 보기 결과를 남기려면 질문·응답·도움 여부를 기록하는 추가 검증 시간이 든다.

### 재검토 조건

첫 보기 과업이 제품 목적과 무관한 행동을 유도하거나 반복 도그푸딩에서 세 구조를 이해해도 실제 감정일기 작성으로 이어지지 않으면 질문과 판정 기준을 재검토한다. 외부 배포 전에는 다양한 사용자의 접근성·이해도 검증 범위를 별도로 결정한다.

## DEC-062 — 목록형 지도를 대체할 평면 버블 감정 우주를 비교한다

- 상태: 제안됨 — 비교 목업·사용자 확인 전 프로덕션 구현 미승인
- 일자: 2026-08-26
- 관련 로그: LOG-20260826-008, LOG-20260826-020, LOG-20260826-024, LOG-20260826-025
- 관련 요구사항: REQ-026, REQ-027, REQ-028, REQ-029
- 관련 결정: DEC-055, DEC-060, DEC-061
- 관련 질문: Q-034, Q-035
- 관련 참고: `docs/references/bubble-emotion-map.md`

### 맥락과 선택지

사용자는 긴 목록을 스크롤하기보다 원형 단어 공간을 손가락으로 돌리거나 밀면서 감정을 발견하는 참고 이미지를 선호한다고 말했다. 충족 감정·미충족 감정·욕구를 각각 큰 공으로 나누는 안과 세 영역을 한 공간에 두는 안을 제안했다.

1. 실제 3D 구체 세 개를 회전한다.
2. 충족 감정·미충족 감정·욕구의 세 버블 공간을 먼저 고른다.
3. 하나의 평면 버블 공간 안에서 세 색 영역을 자유롭게 오간다.

### 현재 제안과 2026-08-26 A안 정정

최초에는 3번을 손가락으로 넓은 평면을 이동하는 `하나의 감정 우주`로 제안했지만, 사용자가 기대한 A안은 구의 앞·뒤 단어가 실제로 회전하는 탐색이었다. 따라서 A안 비교 목업은 구 표면 좌표를 2D로 투영한 `하나의 감정 구`로 정정한다. 전체 감정 161개·충족 70개·미충족 91개·욕구 110개를 필터로 전환하며 실제 카탈로그 271개를 연결한다. 구를 돌리면 뒤쪽 단어가 앞으로 나오고 버블을 눌러 복수 선택한다.

자동 연속 회전과 무거운 3D 물리 엔진은 사용하지 않는다. 검색과 구조화된 전체 목록을 대체 탐색·접근성 경로로 남기고, 모션 감소·저사양 Android·한글 겹침을 별도로 검증한다.

이 제안은 DEC-055의 한 장 지도와 분류 선택 비강요를 보존한다. 버블 크기는 감정 강도나 중요도를 자동 표현하지 않으며, 지속적인 물리 애니메이션과 실제 3D 회전은 기본안에서 제외한다.

### 2026-08-26 사용자 재평가 — 3D 구안 미승인, 평면 패킹안 재비교

사용자는 구형 투영 목업이 수정될수록 참고 이미지보다 빈약하고 글자가 겹쳐 보인다고 평가했다. 따라서 구형 A안을 승인된 방향으로 간주하지 않는다. 참고 이미지의 실제 장점은 검은 배경이나 3D 구체가 아니라, 크기가 다른 원이 서로 겹치지 않고 화면을 채우며 손가락으로 넓은 공간을 이동해 단어를 발견하는 `평면 패킹 버블 지도`에 가깝다.

다음 비교에서는 기존 A안을 더 미세 조정하기보다 다음 C안을 우선한다.

- 충족 감정·미충족 감정·욕구의 색상 영역이 하나의 넓은 2D 공간에 이어진다.
- 원은 서로 겹치지 않고 화면을 빈틈없이 채우며, 대표 단어는 크게 보이되 크기를 감정 강도나 중요도로 오해하지 않도록 안내한다.
- 손가락 드래그로 지도를 이동하고, 누른 원은 중앙으로 부드럽게 이동·확대해 선택과 비슷한 단어를 읽게 한다.
- 확대·축소를 강요하지 않고 검색·분류 바로가기·전체 목록을 동등한 경로로 둔다.

이 C안도 아직 `제안됨`이며 사용자 시각 확인 전 프로덕션 구현으로 승격하지 않는다.

### 장점과 감수하는 비용

- 긴 동일 칩 목록보다 감정 단어를 발견하고 둘러보는 느낌을 강화할 수 있다.
- 충족·미충족 감정과 여러 욕구를 한 기록에 함께 선택할 수 있다.
- 현재 위치, 전체 구조와 화면 밖 단어의 존재가 불명확해질 수 있다.
- 드래그·확대와 버블 충돌 구현은 단순 세로 목록보다 복잡하며 저사양 Android 성능을 별도 검증해야 한다.
- TalkBack·키보드·모션 감소 사용자는 시각적 공간과 동등한 검색·목록 경로가 필요하다.

### 결정 게이트

기존 컬러 개요형 목업, `하나의 감정 우주`, `세 개의 큰 공`을 작은 상호작용 목업으로 비교한다. `docs/ui-qa-guide.md`의 첫 보기 과업과 Android 접근성·성능 위험을 기록해 사용자에게 제시한 뒤 Q-035에서 탐색 구조를 결정한다. QA나 AI가 사용자의 미감 결정을 대신하지 않는다.

2026-08-26 사용자 정정에 따라 최종 비교 화면은 같은 로컬 서버의 세 탭으로 유지한다. A안은 기존 회전 감정 구, B안은 기존 세 개의 큰 공, C안은 서로 다른 크기의 원 271개가 겹치지 않고 이어지는 마음의 섬이다. 별도 시안에서 이름을 다시 A/B로 붙여 기존 후보를 대체하지 않는다.

### 2026-08-26 비교 후 권고 — C+ `촘촘한 마음 지도`

A·B·C를 같은 휴대폰 폭에서 다시 비교한 현재 권고는 어느 안도 그대로 확정하지 않고 C안을 다음과 같이 보정한 C+다. A안은 구를 돌리는 재미가 있지만 한 화면에서 읽을 수 있는 단어가 약 9~12개뿐이고 구 뒤편의 전체 구조를 알기 어렵다. B안은 세 분류를 즉시 이해하기 쉽지만 사용자가 충족·미충족·욕구 중 하나를 먼저 고르게 하므로 섞인 마음을 자유롭게 오가는 흐름에 한 단계가 추가된다. 현재 C안은 전체 카탈로그와 자유 이동을 보존하지만 원 사이 여백과 행렬 느낌 때문에 사용자가 기대한 `붙어 있는 감정 공간`과 첫눈의 구조가 아직 약하다.

C+는 충족·미충족·욕구를 삼각형처럼 맞닿은 세 군락으로 배치하고, 시작 위치를 세 군락의 경계로 둔다. 첫 화면에서 세 영역 이름과 읽을 수 있는 대표 단어 약 18~24개가 함께 보여야 하며, 화면 가장자리의 잘린 군락은 더 넓은 공간이 이어진다는 단서로만 사용한다. 원은 실제 크기에 따라 4~6px 정도의 시각 간격으로 원형 패킹하되 모든 선택 항목의 실질 터치 영역은 Android 권고인 최소 48dp를 지킨다. 크기 차이는 단어 길이와 화면 리듬만 표현하고 감정 강도·중요도를 뜻하지 않는다.

B안의 장점인 세 영역의 명료성은 별도 입구 화면으로 두지 않고 상단 `충족·미충족·욕구` 나침반으로 흡수한다. 나침반을 누르면 해당 군락으로 이동하지만 다른 군락 선택은 유지한다. 검색은 단어가 있는 위치로 지도를 이동하고, 단어를 누르면 중앙에서 읽기 쉽게 확대하며, 하단 선택 선반에서 여러 감정과 욕구를 함께 확인한다. 손가락 이동을 사용할 수 없는 경우에는 전체 목록·검색·TalkBack 순차 탐색을 동등한 경로로 제공한다.

이 권고는 현재 시안과 외부 제품의 구조를 바탕으로 한 AI 제안이며 아직 사용자 확정이 아니다. `How We Feel`의 세밀한 감정 어휘 발견, `Daylio`의 빠른 첫 선택, Mood Meter의 즉시 이해되는 영역 구조를 그대로 복제하지 않고 Inside Me의 충족·미충족·욕구 자기 탐색에 맞게 결합한 추론이다.

### 2026-08-26 운영자 관점 재권고 — C안 `세 개의 마음 방`

사용자는 세 군락을 한 공간에 섞거나 271개를 긴 세로 지도로 이어 보여 주는 방식 모두가 스스로 감정을 찾는 시간을 만들지 못한다고 평가했다. 운영자 관점에서는 `전체를 한번에 보여 주기`보다 `큰 맥락을 알아차리고 관련 말 사이에서 정확한 표현을 찾기`를 우선한다.

- 첫 화면에 `충족 감정 70 / 미충족 감정 91 / 욕구 8개 영역`의 세 개 독립된 마음 방을 보여 준다. 어느 방이 정답이나 의무 순서라는 표현은 사용하지 않는다.
- 충족·미충족 감정 방 안에서는 정본 카탈로그의 의미 그룹별로 단어를 나란히 보여 준다. 요소는 전부 같은 원이 아니라 타원·캡슐·조약돌 모양을 반복해 읽기와 공간 리듬을 함께 만든다.
- 욕구 방은 8개 영역을 먼저 보여 준 뒤 선택한 영역의 세부 욕구를 펼쳐 본다. 이는 원본 110개를 축약하지 않고 의미 단위로 탐색하는 방식이다.
- 방을 바꾸어도 복수 선택을 유지해 하나의 상황에서 충족과 미충족이 함께 있는 경우를 막지 않는다.
- 검은 배경, 정확한 원형 패킹, 외부 제품의 배색·서체·배치는 사용하지 않고 Inside Me의 크림 배경·소프트 파스텔·명확한 선택 상태를 사용한다.

이 변경은 Q-035에서 비교할 `제안됨` 상태다. 사용자가 C안의 첫 화면, 감정 방 내 스크롤, 욕구 8개 영역 진입과 방 전환 후 선택 유지를 휴대폰에서 확인하기 전에는 DEC-055를 대체하거나 프로덕션 UI로 승격하지 않는다.

2026-08-26 사용자 요청에 따라 C+를 실제 비교 목업으로 반영했다. 한 장의 타원형 지도 안에서 271개 원을 육각형에 가까운 촘촘한 패킹으로 연결하고, 충족 감정 70개는 왼쪽 위, 미충족 감정 91개는 오른쪽 위, 욕구 110개는 아래에 이어지도록 했다. 첫 화면은 세 군락의 경계를 보여 주며 상단 세 나침반, 검색, 손가락 이동, 선택 확대와 복수 선택을 직접 시험할 수 있다. 이 목업 구현도 사용자 시각 승인 전까지 프로덕션 결정으로 승격하지 않는다.

2026-08-26 사용자 시각 확인에서 C+는 원이 지나치게 붙어 복잡하고 감정을 읽을 여백이 부족하다고 평가됐다. 따라서 C+의 최대 밀도는 현재 후보에서 제외하고, 직전 C안의 느슨한 탐색 경험을 발전시킨 C2 `여백 있는 마음 지도`로 대체한다. C2는 세 군락이 이어지는 구조와 나침반·검색·이동·복수 선택은 유지하되 원 사이 최소 시각 간격을 약 20px로 늘리고, 색면·테두리·그림자의 강도를 낮춰 첫 화면에 읽을 수 있는 원 약 20~30개가 보이도록 한다. C2도 사용자 재확인 전까지 `제안됨`이다.

2026-08-26 추가 사용자 피드백에 따라 C2의 단어 선택 동작도 사용자 주도로 보정한다. 원을 누를 때마다 선택 원을 중앙으로 옮기는 자동 재중앙 정렬은 탐색 위치를 잃게 하고, 스스로 주변 단어를 찾아보는 의미를 약화하므로 제거한다. 중앙 단어를 선택하면 지도 위치는 그대로 유지하고, 화면 가장자리에서 일부 잘린 단어를 선택한 경우에만 단어가 안전 영역에 들어오도록 가로·세로 각각 최대 72px 이내에서 부드럽게 이동한다. 분류 나침반과 검색은 사용자가 이동을 명시했으므로 해당 군락·단어로 이동한다.

2026-08-26 사용자 정정으로 C2의 세 군락 혼합 배치도 현재 후보에서 제외한다. 가장 쉬운 구조는 전전 시안처럼 `충족 감정 → 미충족 감정 → 욕구`를 위에서 아래로 명확하게 쌓는 세로 지도다. 현재 C안은 충족 감정 70개를 첫 구역, 미충족 감정 91개를 두 번째 구역, 욕구 110개를 마지막 구역에 배치하고 상단 세 버튼으로 각 구역의 시작점에 바로 이동한다. 한 화면에 세 색을 섞어 보여 주려 하지 않고, 현재 구역 제목과 단어만 여백 있게 읽도록 한다. 선택 위치 유지·가장자리 소폭 이동·검색·전체 목록은 그대로 유지한다.

### 2026-08-26 최신 상태 정정

위 C+·C2·세로 지도는 시간 순서상 거쳐 간 이전 비교안이며, LOG-20260826-025에서 현재 비교 C안이 `세 개의 마음 방`으로 대체됐다. 이 정정은 시안 승인이 아니라 현재 비교 대상의 식별이며, 사용자 휴대폰 확인 전까지 `제안됨`을 유지한다.

## DEC-063 — 버블 탐색 원리만 참고하고 구체적인 UI 표현은 독자 설계한다

- 상태: 제안됨 — 사용자 시안 확인과 출시 전 전문가 검토 필요
- 일자: 2026-08-26
- 관련 로그: LOG-20260826-016
- 관련 요구사항: REQ-029
- 관련 결정: DEC-062
- 관련 질문: Q-034, Q-035
- 관련 참고: `docs/references/ui-ip-risk-review.md`

### 맥락

사용자가 제공한 검은 배경의 원형 감정 지도 화면은 공식 자료상 `How We Feel` 앱의 실제 화면으로 확인됐다. 사용자는 유사한 방향으로 상용화할 경우 법적 문제가 있는지 물었고 변호사 역할의 독립 검수를 요청했다. 실제 변호사는 아니지만 별도 AI 검수자가 한국의 저작권·화상디자인권·부정경쟁 위험을 비관적으로 검토했다.

### 제안

`감정을 원형 공간에서 발견한다`, `색으로 분류한다`, `손가락으로 이동한다`는 추상적 탐색 원리만 참고한다. 검은 배경·동일한 4색 영역·원 크기와 위치·세리프 글꼴·잘린 가장자리·상단 원형 컨트롤·동일한 동작의 조합은 재현하지 않는다.

Inside Me 시안은 밝은 크림 바탕, 충족 감정·미충족 감정·욕구의 세 흐름, 한국어 산세리프, 독자적인 선택 선반과 이동 구조를 사용한다. 원본 자산·문구·코드·색상값을 복사하지 않고, 설계·배치 알고리즘·변경 이력을 보존한다.

### 감수하는 비용과 재검토 조건

- 원본과 시각적으로 멀어질수록 사용자가 좋아했던 강한 색 원형 밀도가 약해질 수 있어 목업 비교가 필요하다.
- 독자 배치·반응형·접근성 구현 비용이 든다.
- 이 제안은 법적 안전을 보장하지 않는다. 한국 상용 출시 전에 KIPRIS·WIPO 권리검색과 저작권·부정경쟁 전문 변호사·변리사의 최종 화면 검토를 완료해야 한다.
- 원본에 가까운 표현이 꼭 필요하면 권리자의 서면 허락을 받는 방향으로 재검토한다.

## DEC-064 — C안을 감정일기의 구현 기준 시안으로 사용한다

- 상태: 확정 — 세부 미감과 상호작용은 Android 피드백에 따라 계속 개선
- 일자: 2026-08-26
- 관련 로그: LOG-20260826-026, LOG-20260826-027, LOG-20260826-028, LOG-20260826-029
- 관련 요구사항: REQ-004, REQ-026, REQ-027, REQ-028, REQ-029
- 관련 결정: DEC-037, DEC-055, DEC-061, DEC-062
- 관련 질문: Q-035

### 맥락

원본 이미지의 전체 어휘는 정본 시드에 들어 있지만 C안의 첫 화면에서는 욕구 8개 영역이 보이지 않아 데이터가 누락된 것으로 인식됐다. 감정 방 안에서는 유기형 버튼도 세 열로 길게 반복돼 단어를 발견하는 공간보다 긴 목록처럼 보였다.

### 확정한 범위

- 세 방 이름은 긴 설명형 제목으로 바꾸지 않고 `충족 감정 / 미충족 감정 / 욕구`를 유지한다.
- 욕구 방 카드에서 자율성, 신체·생존, 사회·정서·상호의존, 놀이·재미, 삶의 의미, 진실성, 아름다움·평화, 자기구현의 8개 영역을 작게 미리 보여 준다.
- A/B/C 비교 탭은 비교 목업에서 유지하되 진한 검정 선택과 강한 외곽선을 낮춘다. 프로덕션 앱에는 비교 탭을 넣지 않는다.
- A안 `회전 감정 구`, B안 `세 개의 큰 공`, C안 `세 개의 마음 방`을 비교한 뒤 C안을 실제 앱에 반영할 구현 기준 시안으로 사용한다.
- 비교 당시의 세 첫 화면과 선택 근거는 `docs/references/emotion-map-candidate-comparison.md`에 보존한다.

### 선택한 C안의 탐색 기준

- 감정 방의 의미 그룹을 `감정의 결` 선택지로 먼저 제공하고, 한 묶음을 고르면 해당 세부 단어만 펼친다. 이는 어휘 삭제가 아니라 전체 70개·91개에 도달하는 단계적 탐색이다.
- 검색은 현재 방·감정의 결·욕구 영역에 갇히지 않고 충족 감정·미충족 감정·욕구 271개 전체의 일치 결과를 함께 보여 준다. 구조화된 전체 목록과 복수 선택 유지도 그대로 둔다.
- 첫 감정 결을 기본 미리보기로 펼치는 현재 목업이 강제 분류처럼 느껴지는지는 Android 검증에서 계속 확인한다.

### 결정의 경계와 감수하는 비용

- C안 선택은 실제 앱에 반영할 정보 구조와 탐색 흐름의 기준선 확정이다. 색상·여백·글꼴·유기형 도형·세부 문구와 전환 동작까지 최종 동결한 결정은 아니다.
- 의미 그룹을 한 단계 거치므로 모든 단어를 동시에 보는 조망은 줄어든다. 대신 8개 또는 3개 묶음 이름, 전체 수량, 검색·전체 목록으로 누락 오해를 막는다.
- 실제 앱 반영 뒤 사용자 휴대폰에서 첫 보기 이해, 감정 결 전환, 단어 선택 피로와 욕구 8개 미리보기의 작은 글자 가독성을 다시 확인해야 한다. 시안 확정은 앱 구현 또는 Android 검증 완료를 뜻하지 않는다.

### 재검토 조건

사용자가 감정의 결을 새로운 정답 분류나 필수 설문으로 오해하거나, 묶음 전환 때문에 원하는 단어를 찾기 더 어려워지거나, 320px에서 욕구 8개 미리보기가 읽히지 않으면 결 선택기를 축소·재배치하고 전체 펼치기 경로를 강화한다.
