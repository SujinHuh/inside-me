# Inside Me 지속 개발 워크플로

- 작성일: 2026-08-19
- 상태: 확정
- 관련 요구사항: REQ-019, REQ-020, REQ-023
- 관련 결정: DEC-020, DEC-028, DEC-034, DEC-035, DEC-036, DEC-038

## 이 문서의 목적

사용자가 `시작해`, `개발 시작해` 또는 현재 단계의 구현을 계속하라고 요청했을 때 AI가 이전 맥락을 다시 묻지 않고 다음 미완료 작업을 선택해 구현, 병렬 분업, 통합, 검증과 인계까지 반복하기 위한 실행 기준이다.

이 문서는 제품의 기능 순서를 정하지 않는다. 무엇을 어떤 순서로 완성할지는 `docs/implementation-plan.md`가 원본이며, 이 문서는 그 계획을 누가 어떻게 수행하고 다음 실행에 어떻게 넘길지를 정한다.

## 문서별 책임

| 문서 | 원본 책임 |
|---|---|
| `docs/requirements.md` | 현재 유효한 제품 요구사항과 MVP 범위 |
| `docs/decisions.md` | 선택지, 결정 상태, 트레이드오프와 재검토 조건 |
| `docs/product-log.md` | 사용자 제품 발화와 당시 해석을 보존하는 추가 전용 로그 |
| `docs/open-questions.md` | 사용자 답변이나 프로토타입 검증이 필요한 질문 |
| `docs/implementation-plan.md` | 구현 단계, 사용자 행동, 완료 조건과 현재 다음 작업 |
| `docs/development-workflow.md` | 역할, 파일 소유권, 병렬 실행, 통합, 검증과 인계 방식 |

같은 상세 내용을 여러 문서에 복사하지 않는다. 구현 순서가 바뀌면 구현 계획을, 역할과 실행 방식이 바뀌면 이 문서를 먼저 갱신하고 다른 문서는 링크와 요약만 맞춘다.

## `시작해`가 의미하는 범위

사용자가 개발 시작 또는 계속 진행을 명시하면 현재 승인된 구현 단계 안에서 다음 작업을 지속한다. 기본 실행 범위는 `docs/implementation-plan.md`의 현재 번호 단계 안에서 가장 작은 세로 조각 하나 또는 PR 하나다. 다음 번호 단계로 넘어갈 때는 사용자 확인을 받는다.

포함하는 작업:

- 저장소와 문서 상태 확인
- 다음 미완료 완료 조건 선택
- 승인된 기술 방향 안의 코드와 합성 테스트 데이터 작성
- 안전하게 분리되는 작업의 병렬 실행
- 관련 테스트, 타입 검사, 린트, 빌드와 로컬 실행
- 실패 수정과 재검증
- 구현 계획 상태, 관련 요구사항, 결정, 질문과 제품 로그 갱신
- 기능 단위의 자동 검증·독립 검수 오류 0개를 확인한 뒤 현재 작업 범위만 로컬 커밋
- DEC-042의 지속 승인에 따른 현재 `inside-me` 개발 브랜치 push와 같은 브랜치 PR 생성·갱신
- 사용자가 이번 요청에서 `계속` 또는 `끝까지`를 명시했다면 같은 단계 안의 다음 작업을 반복

포함하지 않는 작업:

- 미확정 제품 범위나 사용자 경험을 임의로 확정
- 유료 서비스, 새 외부 계정이나 복잡한 인프라 도입
- API 키, 인증정보 또는 민감한 기록의 제공·전송
- 사용자의 Android 폰에서 QR 스캔, 권한 승인이나 설치를 대신했다고 간주
- PR 병합, 외부 배포, 스토어 제출 또는 실제 사용자 공개
- 실제 감정일기나 음성·전사를 테스트와 로그에 사용

DEC-042에 따라 `시작해`는 완료한 기능 단위를 현재 `inside-me` 개발 브랜치에 커밋·push하고 같은 브랜치의 PR을 생성·갱신하는 범위까지 포함한다. 새 작업 브랜치의 이름과 기준은 구현 계획에서 확인하고, 다른 저장소·브랜치 원격 변경, force push, PR 병합과 배포는 항상 별도 승인으로 남긴다.

## 외부·폰 원격 접속 환경 모드

사용자가 외부에서 폰으로 Codex에 접속 중이라고 알리면, 사용자가 다시 기기 확인이 가능하다고 말할 때까지 다음 제약을 현재 실행 환경으로 유지한다.

- 사용자는 폰으로 대화만 할 수 있고 개발 Mac, 터미널, Expo QR, Android Expo Go 화면과 로컬 네트워크를 직접 조작하거나 확인할 수 없다고 간주한다.
- Android 실기기 확인, QR 스캔, 앱 재실행, 권한 승인, APK 설치와 눈으로 보는 UI 확인을 요청하지 않는다. 기존 실기기 작업은 `대기`로 보존하고 자동 검증으로 완료 처리하지 않는다.
- 기기·계정·비밀 키·실제 외부 API·과금에 독립적이고 자동 테스트로 검증 가능한 계약, 순수 핵심 로직, 합성 데이터 테스트와 문서 작업만 선택한다.
- 현재 환경 제약은 `docs/implementation-plan.md` 상단에 기록하고, 다음 작업 인계에서도 미검증 실기기 범위를 반복해 알린다.
- 사용자가 Mac 또는 Android 폰을 직접 확인할 수 있다고 새로 말하면 그때 이 모드를 해제하고, 대기 중인 실기기 게이트를 새 플랫폼 기능보다 먼저 재개한다.

책임:

- Expo 프로젝트, 설정, 잠금 파일과 실행 명령 관리
- 모든 `app/**` 진입점, `src/composition/` 조합 루트와 Provider 및 공통 라우트 연결

- 병렬 작업의 범위와 파일 소유권 지정
- 작업 결과 검수, 통합과 전체 흐름 실패 수정
- Android Expo Go 실행 준비와 사용자 확인 요청
- 제품 문서 ID, 커밋과 PR 본문의 최종 관리

주 에이전트만 수정하는 파일:

- 모든 `app/**`, 조합 루트와 Provider

- 루트 배럴 파일
- `README.md`, `AGENTS.md`, `.github/`와 `docs/`

#### 작업자 A — 앱 핵심·로컬 저장 담당

확정 소유 경로:

- `src/core/entries/`
- `src/infrastructure/storage/`
- 위 영역의 단위 테스트

책임:

- 날짜를 기준으로 하루 한 기록을 생성하거나 갱신
- 탐색기의 제안과 사용자가 확정한 감정·욕구를 분리
- 날짜별 조회, 월별 목록, 수정, 완전 삭제와 앱 재시작 복원
- 중복 저장, 저장 실패와 손상 데이터의 명시적 오류 처리
- 저장 성공 전 작성 중인 내용을 지우지 않는 계약
- 향후 데이터 마이그레이션을 위한 스키마 버전 경계
- 전체 기록 내보내기용 버전 포함 직렬화와 무결성 검증

작업자 A는 `src/core/contracts/`의 타입과 포트를 읽어서 구현하되 직접 바꾸지 않는다. 변경이 필요하면 주 에이전트에게 계약 변경을 요청한다.

작업자 A는 전통적인 서버 백엔드 담당이 아니다. 첫 MVP의 기록은 현재 기기에 저장되므로 앱 안의 비화면 핵심 규칙과 저장 구현을 담당한다.

확정 소유 경로:

- `src/features/emotion-review/`

- 자유 글 입력, 키보드 대응, 빈 입력 안내와 초안 보존

- 사용자가 AI 도움 없이도 선택을 확정하고 저장으로 진행하는 흐름
- 사용자의 선택, 수정, 직접 추가와 감정 강도 확인
- AI 또는 임시 탐색기 제안을 자동으로 확정하지 않는 화면 상태
- 저장 실패 후에도 입력과 선택을 유지하는 사용자 흐름
- 기존 기록을 다시 열어 수정하고 저장하는 화면 흐름

- 민감정보 안내와 사용자 확인을 거친 삭제·전체 기록 내보내기 진입

### 2단계 — 실제 AI 연결

실제 AI 비밀 키와 외부 전송이 필요해지면 프론트엔드와 서버 백엔드를 분리한다.

#### AI 경험 프론트엔드 담당

- 외부 전송 범위와 이유 안내
- 한 번에 질문 하나를 보여 주는 대화 UI
- 감정 후보와 사용자의 최종 확인 분리
- 로딩, 취소, 네트워크 실패와 재시도 시 초안 보존
- 음소거와 텍스트 대체 경로

#### AI 중계 서버 백엔드 담당

- 비밀 키를 클라이언트 번들 밖에 보관
- AI 공급자 호출과 교체 가능한 어댑터
- 요청·응답 스키마 검증
- 단정·진단 표현을 막는 안전 검사와 실패 응답
- 데이터 보존·학습 사용 정책에 맞춘 최소 전송
- 일기 원문과 전사를 일반 로그에 남기지 않는 오류 처리

실제 AI 공급자, 비용과 외부 전송 기준은 Q-013이 해결되기 전에는 임의로 확정하지 않는다. 프론트엔드와 서버를 병렬화하기 전에는 서버 런타임·배포 경계·접근 통제, API 스키마와 오류 의미, 멱등성, 취소·시간 초과, 로그 민감정보 제거를 먼저 결정하고 공통 계약으로 고정한다.

### 3단계 이후 — 음성·알림·PWA

기능이 추가될 때도 핵심 기록 흐름은 공유하고 플랫폼 경계만 별도 담당으로 둔다.

- 음성 플랫폼 담당: 녹음, 권한, 전사, 성공 후 원본 오디오 삭제와 실패 시 임시 파일 정리
- 알림 담당: Android 로컬 알림, 미루기, 건너뛰기와 권한 실패
- 웹·PWA 담당: 반응형 화면, 웹 저장, manifest, 오프라인 시작 화면과 웹 알림 대안
- 주 에이전트: 공통 계약, 통합, Android·웹 회귀 검증과 문서 갱신

## 공통 계약 고정 규칙

병렬 작업을 시작하기 전에 주 에이전트가 다음 계약을 최소한으로 고정한다.

- `src/core/contracts/entry.ts`: 날짜 키와 시간대, 초안·확정 기록, 감정·욕구 후보와 사용자 확정 결과 타입
- `src/core/contracts/entry-repository.ts`: 날짜별 조회, 월별 조회, 저장과 삭제 포트
- `src/core/contracts/entry-export.ts`: 저장소와 분리된 버전 포함 내보내기 데이터와 직렬화 계약
- `src/core/contracts/emotion-explorer.ts`: 임시 탐색기와 실제 AI가 공유할 요청·응답 형태
- `src/core/contracts/emotion-vocabulary.ts`: 감정·욕구 어휘, 탐색 분류와 자기 선택·AI 제안·최종 확정 결과의 구분
- `src/core/vocabulary/`: IMP-003에서 주 에이전트가 고정하는 구조화된 어휘 데이터. 기능 작업자는 읽기 전용으로 사용함
- `src/navigation/contracts.ts`: 실제 존재하는 Expo Router typed route와 안전한 전달 값. 아직 없는 경로를 수동 목록으로 미리 만들지 않음
- `src/platform/files/export-file-port.ts`: 내보내기 파일 생성, OS 공유, 취소·성공·실패 후 임시 cache 정리 포트
- `src/testing/fakes/`: 기록 저장소 테스트 대역과 합성 fixture
- `src/infrastructure/exploration/`: 실제 AI 전까지 앱에서 사용하는 로컬 결정적 탐색기 어댑터. 테스트 전용 경로에서 composition으로 역참조하지 않음
- 디자인 토큰과 로딩·빈 상태·오류 상태 공통 컴포넌트

각 포트의 정확한 export 시그니처, 성공 결과와 구분 가능한 오류 타입을 기반 커밋에서 고정한다. 작업자는 이 파일을 읽기 전용으로 사용하고, 공통 계약 변경은 주 에이전트가 영향 범위를 확인한 뒤 먼저 통합한다.

작업자가 공통 계약 변경이 필요하다고 판단하면 직접 수정하지 않고 다음 내용을 주 에이전트에게 전달한다.

- 막힌 사용자 흐름
- 필요한 계약 변경
- 영향을 받는 작업자와 파일
- 호환성·마이그레이션 영향
- 변경하지 않을 때 가능한 대안

## 클린 코드 적용 규칙

모든 구현은 `docs/clean-code-guidelines.md`를 적용한다. 주 에이전트는 자동 검증 전에 해당 체크리스트를 확인하고, 서브에이전트는 독립 검수에서 실제 코드가 이 기준을 지키는지 확인한다.

- 이름이 실제 책임보다 넓거나 좁으면 구현 완료 전에 고친다.
- 저장·JSON·마이그레이션 경계는 TypeScript 타입만 신뢰하지 않고 전체 구조를 parser로 검사한다.
- parser는 원본 객체를 통과시키지 않고 허용된 필드만 새 값으로 반환한다.
- `app/` 라우트는 feature 화면과 조합 루트를 연결하는 얇은 진입점으로 유지한다.
- 실제 Expo Router 파일과 typed route를 라우트의 단일 원본으로 삼고 별도 수동 목록을 중복 관리하지 않는다.
- fixture, CRUD, 경계 검증, 실패 주입이 한 테스트 파일에 누적되면 책임별로 나누고 공통 builder를 사용한다.
- ID·시각 factory, clone과 오류 결과는 실제 계약을 왜곡하거나 책임을 숨기지 않게 이름과 테스트로 보장한다.
- 리팩터링 제안은 현재 요구사항을 깨는 오류와 구분하며, 다음 단계의 안전한 구현을 막는 항목만 현재 게이트에서 수정한다.

## 병렬 작업 시작 조건

다음 조건을 모두 만족할 때만 병렬 구현한다.

- 현재 단계와 완료 조건이 확정되어 있다.
- 공통 계약과 각 작업자의 입력·출력 경계가 정해져 있다.
- 담당 파일과 수정 금지 파일이 겹치지 않는다.
- 각 작업을 독립적으로 검증할 방법이 있다.
- 한 작업의 미완료가 다른 작업의 파일 생성을 막지 않는다.
- 실제 감정일기 대신 합성 데이터만 사용한다.
- 기준 커밋 SHA, 작업 시작 전 변경 파일 목록과 작업자별 수정 금지 파일을 기록한다.

조건을 만족하지 못하면 주 에이전트가 기반 작업을 먼저 완료한다.

같은 작업 디렉터리를 공유하는 병렬 작업자는 소유 경로의 표적 테스트만 실행한다. 병렬 실행 중에는 의존성 설치, 전체 포맷, 코드 생성, 전체 타입 검사·린트·빌드를 하지 않는다. 모든 작업자가 멈춘 뒤 주 에이전트가 하나의 스냅샷에서 전체 검증을 실행한다. 독립 커밋과 전체 검증이 필요하면 처음부터 별도 worktree를 사용한다.

## 작업 지시 형식

주 에이전트는 작업자에게 다음 형식으로 한정된 업무를 전달한다.

```text
목표:
사용자가 겪을 동작:
기준 커밋 SHA:
작업 시작 전 변경 파일:
소유 경로:
읽어야 할 요구사항·결정:
사용할 공통 계약:
수정 금지 파일:
정상 흐름 완료 조건:
실패 흐름 완료 조건:
실행할 검증:
주 에이전트에게 전달할 결과:
```

한 작업자에게 서로 무관한 기능, 공통 문서 갱신과 Git 작업을 함께 맡기지 않는다.

## 작업자 인계 형식

각 작업자는 작업이 끝나면 다음을 주 에이전트에게 전달한다.

```text
구현한 사용자 동작:
변경 파일:
사용하거나 가정한 계약:
실행한 검증과 결과:
검증 환경·명령·기준 커밋 SHA:
실행하지 못한 검증과 이유:
남은 위험:
통합 때 필요한 연결:
문서에 반영할 제안:
실행 중인 프로세스·포트와 종료 여부:
```

작업자는 주 에이전트가 명시적으로 위임하지 않는 한 제품 로그, 결정, 요구사항, 질문, 공통 설정, Git 스테이징과 커밋을 수정하지 않는다.

## 지속 구현 루프

### 1. 현재 상태 확인

- 현재 브랜치, HEAD SHA, 작업 트리와 원격 상태를 기준선으로 기록한다.
- `main`에서는 새 작업 브랜치 없이 구현하지 않는다.
- 시작 전 존재한 변경 파일은 명시된 작업 범위가 아니면 수정하거나 스테이징하지 않는다.
- `docs/requirements.md`, 관련 결정·질문·최근 로그를 읽는다.
- `docs/implementation-plan.md`의 실행 상태 원장에서 현재 작업 ID와 선행 조건을 찾는다.
- 기존 사용자 변경과 실행 중인 작업을 보존한다.

### 2. 다음 작업 선택

- 현재 단계의 사용자 행동을 실제로 한 칸 앞으로 옮기는 가장 작은 작업을 고른다.
- 문서만 정리하고 사용자 흐름이 진전되지 않는 작업을 반복하지 않는다.
- 미확정 선택이 필요하면 되돌리기 쉬운 임시 계약인지, 사용자 결정이 필요한 범위 변경인지 구분한다.

### 3. 기반과 병렬 가능성 확인

- 공통 계약, 라우트, 토큰과 테스트 기반이 없으면 주 에이전트가 먼저 만든다.
- 서로 겹치지 않고 독립 검증할 수 있는 작업만 병렬화한다.
- 병렬 작업마다 소유 경로와 수정 금지 파일을 명시한다.

### 4. 구현

- 입력부터 저장과 다시 보기까지 현재 단계의 세로 흐름을 유지한다.
- 확정 스택의 공식 최소 패키지도 버전, 라이선스, 데이터 전송 여부를 기록하고 잠금 파일에 고정한다. 그 밖의 프로덕션 의존성, 원격 설치 스크립트, 계정 로그인과 외부 서비스는 필요성, 대안, 비용, 개인정보 영향과 제거 가능성을 설명하고 사용자 확인을 받는다.
- 실패 시 작성 내용과 기존 기록을 잃지 않는 경로를 함께 구현한다.
- 삭제·손상·마이그레이션 테스트는 고유 namespace 또는 임시 DB의 합성 데이터에서만 실행한다. 실제 앱 저장소 전체 초기화 명령은 사용하지 않는다.
- 스키마 변경은 copy-on-write 또는 원자적 쓰기로 이전 데이터를 보존하고 실패 시 이전 버전으로 돌아가는 경로를 검증한다.

### 5. 통합과 검증

- 주 에이전트가 작업자 결과를 읽고 공통 계약 위반과 파일 충돌을 확인한다.
- 작업자 A의 저장소 계약 테스트, 작업자 B의 가짜 저장소 기반 작성·확정·저장 의도, 작업자 C의 seeded 가짜 저장소 기반 달력·상세를 차례로 검증한다.
- 그 뒤 주 에이전트가 실제 저장 어댑터를 조합 루트에 연결하고 Android 전체 흐름을 검증한다.
- 정상 흐름뿐 아니라 빈 입력, 중복 저장, 저장 실패, 재시작 복원과 삭제를 검증한다.
- 저장소에 정의된 테스트, 타입 검사, 린트와 빌드를 실행한다.
- Android 실제 기기 확인이 필요한 지점에서는 필요한 사용자 행동을 정확히 요청한다.
- 에뮬레이터, 웹, 타입 검사나 빌드 성공을 Android 실기기 성공으로 대신하지 않는다.
- 같은 원인으로 세 번 실패하면 검증 수준을 낮추지 말고 `차단됨`으로 기록한다. 각 시도의 명령·오류·변경을 남긴다.
- 개발 서버와 감시 프로세스의 PID·포트를 인계에 기록하고, 사용자가 쓰는 프로세스가 아니면 작업 후 종료한다.

### 6. 서브에이전트 독립 검수 게이트

코드, 공통 계약, 저장 스키마, 의존성, 설정 또는 사용자 동작을 바꾸는 가장 작은 구현 단위마다 다음 구현 전에 독립 검수를 통과한다. 오탈자 수정이나 실행 결과만 추가하는 로그 갱신처럼 제품·실행 동작을 바꾸지 않는 순수 문서 작업은 제외할 수 있다. 다만 에이전트 지침, 안전 규칙, 상태 원장과 완료 기준을 바꾸는 문서는 구현과 같이 검수한다.

#### 검수 준비

- 주 에이전트가 구현과 자동 검증을 끝낸 뒤 현재 작업을 `독립 검수 대기`로 바꾸고 다음 구현을 시작하지 않는다.
- 검수자에게 작업 ID, 기준 SHA, 검수 대상 SHA 또는 미커밋 diff, 변경 파일, 관련 REQ·DEC·Q·LOG, 실행한 검증과 미검증 범위를 전달한다.
- 검수 서브에이전트는 해당 구현에 참여하지 않은 에이전트로 배정하고 소스, 문서와 Git 상태를 수정하지 않는 읽기 전용 검수를 지시한다.
- 작은 변경은 최소 1명이 검수한다. 공통 계약·저장·마이그레이션·보안·개인정보·외부 전송·여러 화면에 걸친 변경은 가능한 서로 다른 관점의 서브에이전트 2명 이상이 검수한다.

#### 검수 관점

- 현재 요구사항·결정·사용자 행동과 구현이 일치하는지
- 정상·실패·취소·재시작 흐름에서 데이터 손실·중복·묵시된 오류가 없는지
- 공통 계약, 계층 방향, 플랫폼 경계와 파일 소유권을 어기지 않았는지
- `docs/clean-code-guidelines.md`에 따라 이름과 실제 책임, 전체 런타임 parser, 얇은 라우트, fixture·테스트 책임 분리가 유지되는지
- 비밀정보, 일기·음성·전사, 외부 전송, 로그, 삭제·내보내기·마이그레이션 안전이 유지되는지
- 자동 테스트가 핵심 회귀와 실패 경로를 실제로 검증하는지, 미검증 항목이 통과로 표시되지 않았는지
- UI 변경이면 Android 화면 크기, 키보드, 스크린 리더, 색상 외 상태 표시와 Inside Me 디자인 원칙을 충족하는지

#### 오류 반영과 통과

- 검수자는 발견 사항을 중요도, 근거 파일·줄, 재현 또는 영향, 구체적 수정안으로 보고한다. 추측이나 취향은 확인된 오류와 구분한다.
- 확인된 오류가 있으면 주 에이전트가 상태를 `진행 중`으로 돌리고 수정한 뒤 관련 자동 검증을 다시 실행한다. 수정된 diff를 같은 관점으로 재검수하여 오류 해소를 확인한다.
- 다음 구현으로 넘어가는 통과 조건은 `확인된 오류 0개`, `관련 자동 검증 통과`, `미검증 범위·남은 제안·위험 기록`, `검수 대상 SHA 또는 diff 기록`이다.
- 낮은 중요도의 개선 제안이 남아도 현재 요구사항의 오류가 아니면 후속 작업으로 기록할 수 있다. 다만 오류인지 제안인지 분명하지 않으면 통과하지 않고 주 에이전트가 근거를 확인한다.
- 같은 원인의 수정·재검증·재검수가 3회 반복되면 검수 수준을 낮추지 말고 `차단됨`으로 기록한다.
- 서브에이전트 독립 검수를 실행할 수 없으면 주 에이전트의 자체 리뷰로 대체하지 않고 `독립 검수 대기`로 멈춘 뒤 사용자에게 알린다.

### 7. 기록과 인계

- 바뀐 동작에 해당하는 요구사항, 결정과 질문을 갱신하고, 제품 대화는 다음 `LOG-*`에 원문과 해석을 추가한다.
- 구현·관련 문서·자동 검증·독립 검수 결과를 기능 또는 통합 커밋 SHA A로 고정한다.
- 구현 계획의 완료 증거에 검증 방법, 실행 명령, 결과, 환경, SHA A와 사용자 확인 여부를 기록하고 다음 작업 포인터를 갱신한다. 미실행이나 사용자 확인 대기는 통과로 표시하지 않는다.
- SHA A를 기록한 원장·상태 문서를 별도 상태 문서 커밋 SHA B로 고정한다. SHA B를 다시 자기 자신 안에 기록하지 않으며, Git 로그와 PR이 최종 상태 커밋을 증명한다.
- SHA B 뒤 작업 트리가 깨끗한지 확인한 다음 현재 개발 브랜치를 push하고, 같은 브랜치의 PR을 생성하거나 전체 변경·검증·상태에 맞게 갱신한다.
- PR 템플릿에 변경 이유, 실제 검증과 미검증 사유, 개인정보·데이터 영향을 기록한다.

### 8. 반복 또는 중단

- 현재 단계의 세로 조각 또는 PR 하나를 통합·검증·인계하면 해당 턴을 종료하고 사용자 체크포인트를 만든다.
- 사용자가 이번 요청에서 `계속` 또는 `끝까지`를 명시한 경우에만 같은 번호 단계 안에서 1단계로 돌아간다. 다음 번호 단계로 넘어가기 전에는 항상 다시 확인한다.
- 자동 검증만 통과하고 서브에이전트 독립 검수를 통과하지 않았다면 완료로 표시하거나 다음 구현으로 넘어가지 않는다.
- 완료 조건을 충족하지 못했으면 완료로 표시하지 않고 원인을 해결한다.
- 아래 중단 조건에 해당하면 현재까지의 결과와 정확한 다음 선택을 사용자에게 전달한다.

## 중단 조건

다음 중 하나에 해당하면 추측으로 진행하지 않는다.

- 제품 범위, 저장 정책 또는 사용자 경험을 크게 바꾸는 미결정 사항
- 유료 서비스, 새 외부 계정, 복잡한 인프라나 공급자 종속 도입
- 민감정보 외부 전송, API 키, 인증정보 또는 개인정보 정책 결정
- 사용자의 Android 폰에서 QR 스캔, 권한 승인, APK 설치 또는 눈으로 확인해야 하는 결과
- 외부 사용자 공개 전 Q-012 위기 대응 흐름 미확정
- PR 병합, 외부 배포, 스토어 제출 또는 되돌리기 어려운 데이터 변경
- 같은 원인의 검증 실패가 세 번 반복되어 현재 정보로 안전하게 해결할 수 없는 상태

중단할 때는 완료된 내용, 실패한 검증, 보존된 데이터, 필요한 사용자 행동과 이후 재개 지점을 남긴다.

## Git과 PR 운영

- 작업 시작 시 기준 브랜치, HEAD SHA와 기존 변경 파일을 기록한다.
- 문서와 기반 변경은 기준 브랜치에서 파생한 작업 브랜치에 먼저 반영한 뒤 병렬 작업을 시작한다.
- `main`에는 문서를 포함해 직접 커밋하거나 푸시하지 않고, 사용자 승인을 받은 PR 병합으로만 반영한다.
- 같은 작업 디렉터리를 공유하면 작업자는 Git 명령을 실행하지 않고 주 에이전트가 한 번에 스테이징·커밋한다.
- 독립 커밋이 필요하면 같은 기반 커밋에서 별도 worktree와 브랜치를 만든다.
- 공통 계약 변경은 먼저 통합한 뒤 기능 브랜치에 반영한다.
- 모든 PR은 `.github/pull_request_template.md`와 `docs/pull-request-guide.md`를 따른다.
- PR 제목과 본문은 한국어로 작성한다. 제목에는 영문 Conventional Commit 접두어를 사용하지 않고 변경 결과를 짧은 한국어 명사형으로 적으며, 코드 식별자·명령·파일명만 원문을 유지한다.
- 커밋 전 `git diff --cached`로 현재 작업 범위 밖의 파일이 섞이지 않았는지 확인한다.
- 기능 단위가 자동 검증과 독립 검수를 통과하면 검수 대상 diff를 기능 커밋 SHA A로 고정하고, 원장에 SHA A를 기록한 상태 문서 커밋 SHA B를 만든다. push 직전 HEAD가 SHA B이고 SHA B의 직접 부모가 SHA A인지 확인한다.
- `SHA_A..SHA_B`의 name-status와 diff는 `README.md`, `docs/implementation-plan.md`, `docs/product-log.md`에서 완료 상태·SHA·다음 포인터를 기록하는 사실 변경만 허용한다. 코드·설정·테스트·AGENTS·workflow·requirements·decisions의 의미 변경 또는 허용 목록 밖 파일이 있으면 SHA A를 다시 정하고 자동 검증·독립 검수를 반복한다.
- push 직전 `git rev-parse --show-toplevel`로 현재 root가 `inside-me`인지, `git remote get-url origin`이 승인된 `https://github.com/SujinHuh/inside-me.git`인지, symbolic current branch가 detached HEAD나 `main`이 아니고 구현 계획의 현재 개발 브랜치와 같은지 확인한다. 하나라도 다르면 중단한다.
- `git status --porcelain`이 비어 있는지 확인한다. 작업 시작 기준에 없던 dirty·untracked 파일, 검수 뒤 바뀐 파일 또는 HEAD 불일치가 있으면 push하지 않고 범위를 분리하거나 사용자 확인을 받는다.
- 전체 게시 범위를 계산하기 직전에 승인된 `origin`에서 `main`만 non-destructive fetch한다. fetch한 `origin/main` SHA와 GitHub API에서 읽은 `SujinHuh/inside-me` live `main` SHA가 같은지 확인하며, fetch·API 조회가 실패하거나 SHA가 다르면 캐시된 ref로 대신하지 않고 원격 게이트에서 중단한다.
- 최신으로 확인한 `origin/main...HEAD`의 commit 목록, name-status와 전체 diff를 확인해 현재 PR 범위 밖의 커밋·파일이 없는지 검수한다. 전체 게시 범위와 PR 제목·본문에서 API 키·토큰·개인키·인증 URL·실제 일기·전사·개인식별정보 패턴을 확인하고, 패턴 검사는 보조 수단일 뿐 안전 판정의 유일한 근거로 사용하지 않는다.
- 위 게이트를 모두 통과하면 검증한 현재 브랜치 하나만 `origin`의 동일 이름 ref로 non-force push한다. tag, 다른 ref와 여러 refspec을 함께 push하지 않으며 force push는 별도 명시적 요청 없이 사용하지 않는다.
- PR 조회는 정확한 `SujinHuh/inside-me` 저장소와 `SujinHuh:<현재 브랜치>` head로 한정한다. 열린 PR이 0개면 `main` base로 만들고, 1개면 head와 base가 각각 현재 브랜치와 `main`인지 확인한 뒤 갱신한다. 여러 개이거나 head·base가 다르면 중단하고 사용자 확인을 받는다.
- PR 본문은 매번 템플릿을 다시 작성한다. 실제 변경 유형만 체크하고, 실행한 검증만 체크하며, 미실행·실기기 확인 대기·개인정보·로컬 데이터·마이그레이션 영향을 명시한다.
- `main...현재 브랜치` PR 전체 diff에 포함된 모든 작업 단위의 완료 기준·자동 검증·독립 검수가 통과하고 미완료 항목이 없을 때만 병합 가능한 PR로 표시한다. 하나라도 남으면 Draft를 유지하고 남은 완료 조건을 적는다. Draft는 완료 게이트를 우회하는 수단으로 사용하지 않고, 완료된 설계 검토 단위이거나 사용자가 미완료 공유를 별도로 요청했을 때만 새로 만든다.
- 이 지속 승인은 현재 `inside-me` 저장소의 기능 완료 브랜치 push와 같은 브랜치 PR 생성·갱신에만 적용한다. 다른 저장소·브랜치 원격 변경, force push, PR 병합, 배포와 스토어 제출은 별도 요청이 필요하다.
- push 또는 PR 작업이 실패하면 로컬 커밋을 보존하고 오류와 재시도 지점을 기록한 뒤 다음 구현으로 넘어가지 않는다. push 성공 뒤 PR이 실패한 부분 성공 상태라면 원격 SHA, PR 미생성·미갱신 상태와 안전한 재시도 명령 범위를 기록한다.
- PR을 병합하거나 배포하지 않은 상태를 완료로 오해하지 않는다.
