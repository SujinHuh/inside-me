# Inside Me UI 브라우저 보조 QA 가이드

- 상태: 반복 검수 기준
- 작성일: 2026-08-26
- 관련 문서: `docs/development-workflow.md`, `docs/device-validation-checklist.md`, `docs/references/ui-qa-standards.md`, `docs/references/hallmark.md`, `docs/references/windows-classic-ui.md`
- 관련 요구사항·결정: REQ-029, DEC-061

## 목적

화면 구현과 목업을 눈으로 한 번 보고 끝내지 않고, 작은 휴대폰 폭에서의 배치와 핵심 상호작용을 Codex가 반복 가능한 순서로 점검한다. 브라우저가 측정할 수 있는 항목과 사람이 판단해야 하는 시각·사용성 항목을 분리하고, Android 실기기 검증의 증거와 섞지 않으며, 실행하지 않은 항목을 통과로 표시하지 않는다.

현재 방식은 Codex가 브라우저를 조작해 화면 크기·DOM·상호작용을 확인하는 **브라우저 보조 QA**다. 대상 URL·기준 Git SHA 또는 목업 식별자·실행 환경을 먼저 기록하고, 그 실행에서 사용한 화면 크기와 시나리오를 같이 남긴다. 선택자·경계값·측정 스크립트가 저장소에 없다면 `절차 반복 가능, 실행 자동화 아님`으로 표시한다. 저장소 CI에서 스크린샷을 자동 비교하는 시각 회귀 시스템은 아직 도입하지 않았다.

QA는 다음 네 층의 증거를 섞지 않는다.

1. 정적·코드 검증: 어휘 수, 접근성 속성, 상태 보존 계약과 테스트 결과
2. 브라우저 보조 QA: 화면 폭별 배치·경계·대비·포커스와 상호작용
3. 사용자 첫 보기 QA: 설명 없이 전체 구조와 탐색 시작점을 이해하는지
4. Android 실기기 QA: 실제 글꼴·키보드·손가락·TalkBack·저장과 재실행

각 층을 통과해야 해당 층만 통과한 것이다. 브라우저 성공을 사용자 이해나 Android 성공으로, 한 명의 도그푸딩 성공을 모든 사용자의 성공률로 확대하지 않는다.

## 실행 전 식별자

- 앱: 기준 Git SHA, 실행 명령, 대상 URL과 route
- 저장소 내 목업: 상대 경로, 실행 명령과 대상 URL
- 저장소 밖 임시 목업: 파일명 또는 세션 식별자, 임시 산출물임, 재실행·보존을 보장하지 않음, 앱 코드·Git 산출물이 아님을 명시

식별자와 실행 방법이 없는 임시 목업 결과는 후속 구현의 재현 증거로 사용하지 않고, 당시 대화의 방향 비교 자료로만 취급한다.

## 적용 시점

- 새 화면 또는 반응형 목업을 만들었을 때
- 색상·글자·간격·고정 바·목록 구조처럼 시각 위계가 바뀌었을 때
- 키보드, 검색, 선택, 스크롤과 다음 행동의 위치가 바뀌었을 때
- Android 실기기에서 잘림·겹침·발견성 문제가 보고됐을 때
- PR을 게시하기 전 자동 검증과 독립 검수 근거를 만들 때

## 기본 화면 크기

| 구분 | 너비 × 높이 | 확인 목적 |
|---|---:|---|
| 작은 휴대폰 | 320 × 720 | 긴 한글, 2열 선택 항목, 고정 UI의 최소 폭 |
| 기준 휴대폰 | 360 × 800 | 기본 Android 도그푸딩 화면 |
| 큰 휴대폰 | 412 × 915 | 넓은 Android 화면의 여백과 정보 밀도 |

필요하면 736px 이상의 데스크톱 웹을 추가하지만 모바일 실패를 데스크톱 성공으로 대체하지 않는다. 화면 높이는 기기별로 달라질 수 있으므로 첫 화면에 무엇이 보이는지와 고정 요소가 본문을 가리는지를 함께 확인한다.

## 브라우저·DOM으로 판정할 항목

1. 초기 렌더에서 오류 화면과 콘솔 오류가 없는지 확인한다.
2. 문서 너비와 실제 콘텐츠 너비를 비교해 의도하지 않은 가로 스크롤을 찾는다.
3. 제목·본문·버튼 문구의 경계를 측정해 잘림·겹침 후보를 찾고 화면 캡처를 남긴다. 의미가 잘 전달되는지는 사람이 판정한다.
4. 웹 버튼·검색·선택 항목의 조작 영역이 프로젝트 기준 44 × 44 CSS px 이상인지 확인한다. Android 네이티브 조작 영역은 실기기에서 별도 확인한다.
5. 키보드만으로 주요 입력과 버튼에 도달하고 포커스 위치를 구분할 수 있는지 확인한다.
6. 색상 없이도 선택·오류·비활성·완료 상태를 이름, 체크 표시와 접근성 상태로 알 수 있는지 확인한다.
7. 화면 크기를 바꾼 뒤 선택·검색·입력 상태가 의도 없이 초기화되지 않는지 확인한다.

## 객관 판정선

- 320 CSS px 너비에서 정보·기능 손실과 의도하지 않은 가로 스크롤 없이 세로로 재배치돼야 한다. 360·412px도 같은 시나리오로 확인한다.
- 일반 크기 본문 텍스트는 배경과 4.5:1 이상, 큰 텍스트와 상태를 전달하는 핵심 그래픽은 3:1 이상의 대비를 유지한다.
- 웹 조작 영역은 프로젝트 기준 44 × 44 CSS px 이상, Android 네이티브 조작 영역은 48 × 48dp 이상을 목표로 한다. WCAG의 더 작은 예외에 기대어 주요 감정 선택 항목을 축소하지 않는다.
- 키보드 포커스를 받은 요소가 고정 헤더·검색·선택 바에 완전히 가려지면 실패다. Inside Me에서는 현재 읽는 단어와 다음 행동도 고정 UI에 실질적으로 가리지 않는 것을 목표로 한다.
- `충족 감정`, `미충족 감정`, `욕구 8개 영역`의 제목과 조작 레이블은 해당 그룹과 행동 목적을 설명해야 한다. 장식색만으로 그룹을 구분하지 않는다.

수치와 외부 근거의 원문·적용 경계는 `docs/references/ui-qa-standards.md`를 단일 참고로 삼는다.

## 감정·욕구 지도 추가 점검

1. 320×720 첫 뷰포트에서 스크롤하기 전에 `충족 감정`, `미충족 감정`, `욕구`의 세 진입 레이블과 `욕구 8개 영역`의 존재·접근 경로가 완전히 노출되고 고정 UI에 가려지지 않으며 조작 가능한지 측정한다. 8개 이름을 첫 뷰포트에 모두 노출하는 것은 필수가 아니며, 욕구 진입 뒤 도움 없이 8개 영역 목록에 접근할 수 있어야 한다. 사용자가 이 구조와 탐색 시작점을 이해하는지는 사용자 첫 보기 QA로 따로 판정한다.
2. 컬러 개요는 선택을 강요하는 단계가 아니라 같은 페이지의 전체 목록으로 이동하는 선택적 탐색 도구여야 한다.
3. 검색하지 않아도 전체 271개 어휘에 도달할 수 있고, 검색하면 충족·미충족 감정과 욕구를 함께 좁혀야 한다.
4. 세 영역의 서로 다른 항목을 복수 선택하고 검색·빠른 이동·화면 크기 변경 뒤에도 선택을 유지해야 한다.
5. 선택 상태는 색만 바꾸지 않고 체크 표시와 `aria-pressed` 또는 동등한 접근성 상태를 함께 제공해야 한다.
6. 선택 현황과 다음 행동은 긴 스크롤 중에도 찾을 수 있어야 하지만, 320px·큰 글자에서 어휘나 시스템 내비게이션을 가려서는 안 된다.
7. 원본 참고 이미지의 넓은 색면과 범주 위계는 살리되, 작은 이미지 글자와 조밀한 정적 표를 그대로 복제하지 않는다.

## 기능 시나리오

합성 표현만 사용해 다음 순서로 점검한다.

1. 컬러 개요에서 충족 감정으로 이동한다.
2. 충족 감정 하나를 선택한다.
3. 미충족 감정으로 이동해 하나를 추가 선택한다.
4. 욕구 영역으로 이동해 하나를 추가 선택한다.
5. 전체 검색에 합성 검색어를 입력해 결과를 좁히고 기존 선택이 유지되는지 확인한다.
6. 검색어를 지우고 세 영역 선택 개수와 전체 선택 목록이 일치하는지 확인한다.
7. 선택 하나를 해제하고 접근성 상태·표시·개수가 함께 갱신되는지 확인한다.

## 사용자 첫 보기 QA

브라우저 측정과 별도로, 대상 화면 버전을 설명하지 않은 상태에서 진행한다. 임의의 시간 제한으로 사람을 재촉하지 않고 다음 과업을 실제로 수행하는지를 본다.

1. 화면을 처음 보여 준 뒤 다음 질문을 그대로 한다: `이 화면에서 어떤 종류의 내용을 볼 수 있고, 원하는 단어를 어떻게 찾을 것 같은지 말해 주세요.`
2. 사용자가 `충족 감정`, `미충족 감정`, `욕구`라는 세 탐색 축을 식별하는지 기록한다.
3. 욕구가 8개 영역으로 이어진다는 구조와 접근 경로를 이해하고, 도움 없이 진입해 `자율성`, `신체적 안녕과 생존`, `연결과 상호의존`, `놀이와 재미`, `삶의 의미`, `진실성과 자기존중`, `아름다움과 평화`, `자기구현과 성장` 목록에 도달하는지 기록한다.
4. 화면 밖에도 전체 목록이 이어지고 검색 또는 세로 스크롤로 접근할 수 있음을 이해하는지 기록한다.
5. 도움 없이 한 시작점을 고르고 실제 감정 또는 욕구 단어를 읽기 시작하는지 확인한다.

다음 중 하나면 실패로 기록한다.

- 진행자가 화면 구조나 시작 위치를 설명해야 했다.
- 사용자가 핵심 탐색을 시작하기 위해 도움을 요청했거나 관찰상 도움이 필요했다.
- 사용자가 세 탐색 축 중 하나 이상을 찾지 못했다.
- 사용자가 욕구가 8개 영역으로 이어진다는 점이나 접근 경로를 이해하지 못했거나, 도움 없이 8개 영역 목록에 도달하지 못했다.
- 271개가 첫 뷰포트에 전부 보여야 하거나 한 범주를 반드시 먼저 확정해야 한다고 오해했다.
- 첫 화면에서 실제 단어를 읽기 시작할 경로를 찾지 못했다.

화면 식별자·Git SHA, 기기와 화면 크기, 위 질문 원문, 사용자 응답 요약, 도움 필요 여부, 첫 실패 지점을 남긴다. 사용자가 `예쁘다`고 말한 것만으로 탐색 성공을 대신하지 않고, 탐색 성공만으로 시각적 만족도를 대신하지 않는다.

## 증거 기록

- 기준 Git SHA 또는 목업 파일 식별자
- 실행 날짜와 화면 크기
- 브라우저로 실행한 시나리오, 자동 측정 여부와 통과·실패
- 첫 화면과 핵심 선택 상태 캡처
- 첫 뷰포트의 세 진입 레이블·`욕구 8개 영역` 접근 요소의 경계 좌표와 가림·조작 가능 여부, 진입 뒤 8개 영역 이름의 도달 결과
- 가로 넘침·44px 터치 영역·콘솔 오류 수
- 대비를 측정한 전경·배경 색상값, 계산 비율과 사용한 측정 도구
- Android 48dp는 React Native Inspector의 레이아웃 경계, `hitSlop`을 포함한 코드의 유효 터치 경계 또는 Accessibility Scanner 등 사용한 측정 방법, 대상 요소와 최소 측정값
- 자동 QA로 확인할 수 없는 Android 항목
- 확인된 오류 ID와 수정 뒤 재검증 결과
- 사용자 첫 보기 질문·응답 요약·도움 필요 여부·첫 실패 지점

앱과 Android 누적 검증 결과의 단일 기록 위치는 `docs/device-validation-checklist.md`다. 설계 선택용 임시 목업은 `docs/product-log.md`에 목업 식별자·임시성·실행 방법·미검증 범위를 남기되, 앱 완료 증거로 사용하지 않는다. Android 사용자의 성공 응답, 기기·OS와 기준 SHA가 없으면 실제 기기 검증을 완료로 바꾸지 않는다.

## 브라우저 보조 QA가 대체하지 못하는 항목

- Android 제조사 키보드가 입력창과 다음 행동을 가리는지
- 실제 손가락으로 스크롤·탭할 때의 피로와 오동작
- TalkBack의 실제 읽기 순서와 발음
- Android 글꼴·확대 설정·시스템 내비게이션 영역 렌더링
- Expo Go 재실행 뒤 SQLite 저장·복원과 공유 화면
- 사용자가 느끼는 감정 집중도와 시각적 만족도

위 항목은 `docs/device-validation-checklist.md`의 실기기 단계에서 별도로 확인한다.

## 실패 처리

- 잘림·겹침·탐색 불가·선택 유실·터치 영역 부족은 확인된 오류로 기록하고 다음 구현으로 넘어가지 않는다.
- 취향 차이와 기능 오류를 구분하되, 사용자가 핵심 선택 지점을 찾기 어렵다고 보고하면 사용성 오류로 추적한다.
- 자동 QA를 통과시키기 위해 어휘를 임의로 줄이거나 요구된 동작을 숨기지 않는다.
- 수정 뒤 같은 화면 크기와 같은 시나리오를 다시 실행하고, 관련 코드 테스트와 독립 검수를 함께 통과해야 한다.
