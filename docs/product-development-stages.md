# Inside Me POC→프로토타입→MVP 제품화 단계

- 상태: 반복 개발 단계와 승격 기준의 단일 원본
- 작성일: 2026-08-26
- 관련 요구사항: REQ-010, REQ-020, REQ-023, REQ-029
- 관련 결정: DEC-042, DEC-057, DEC-061, DEC-062
- 관련 문서: `docs/implementation-plan.md`, `docs/development-workflow.md`, `docs/ui-qa-guide.md`, `docs/device-validation-checklist.md`

## 문서 목적

Inside Me는 작은 POC로 기술 가능성을 확인한 뒤 실제 사용 피드백을 근거로 프로토타입과 MVP로 승격한다. `POC 중심`은 기능을 계속 임시로 만든다는 뜻이 아니라, 불확실한 문제를 가장 작은 검증물로 먼저 확인하고 증거가 있는 부분만 제품 코드·데이터·QA 범위로 확장한다는 개발 방식이다.

현재 전체 앱은 POC 단계에 머물러 있지 않다. 글 기록의 핵심 흐름은 MVP 제품화 중이고, 버블 감정 지도·실제 음성·실제 AI처럼 아직 결정·기기·외부 서비스 검증이 필요한 부분만 별도의 POC 또는 프로토타입으로 다룬다.

## 단계별 의미와 통과 기준

| 단계 | 확인할 질문 | 허용 산출물 | 다음 단계 통과 조건 | 완료라고 표현하면 안 되는 것 |
|---|---|---|---|---|
| POC | 기술적으로 가능한가, 핵심 위험을 분리할 수 있는가 | 합성 데이터, fake 어댑터, 최소 계약·화면 | 핵심 가능성·실패 원인과 폐기 가능한 경계 확인 | 실제 사용자 가치·실기기 제품 완료 |
| 상호작용 프로토타입 | 사용자가 구조와 시작 방법을 이해하는가 | 저장소 내 HTML 목업, 제한된 대표 데이터 | 후보 비교, 첫 보기 QA, 사용자 방향 결정 | 전체 271개·저장·접근성·성능 완료 |
| 기능 세로 조각 | 입력부터 결과까지 한 경로가 안전하게 동작하는가 | 앱 코드, 계약·단위·화면 테스트 | 정상·실패·취소·데이터 보존 검증과 독립 검수 | 다른 조각과 실제 기기 통합 완료 |
| 텍스트 도그푸딩 MVP | 본인 Android에서 매일 글 기록을 사용할 수 있는가 | 전체 271개, 로컬 저장·달력·선택적 실제 AI | IMP-106·204C·205D와 개인정보·비용 게이트 통과 | 음성·핑퐁·알림·외부 배포까지 완료 |
| 후속 제품화 | 실제 음성·핑퐁·APK 등 다음 가치가 안정적인가 | 플랫폼 어댑터·배포 빌드 | 기능별 기기·외부 서비스·안전 검증 | 검증하지 않은 플랫폼·사용자 일반화 |

## 현재 기능의 단계 분류

| 기능 | 현재 단계 | 근거·남은 게이트 |
|---|---|---|
| 글 기록→감정·욕구 선택→SQLite 저장→달력 | 기능 세로 조각 완료, MVP 실기기 통합 진행 | IMP-101~107C 완료, IMP-106 DV-03 이후 대기 |
| 컬러 한 장 마음 지도 | 구현 프로토타입을 앱에 통합했으나 UX 재검토 | 전체 271개 구현, UX-01과 Q-034·Q-035 결정 대기 |
| 버블 감정 지도 | 상호작용 프로토타입 | DEC-062 제안, A/B HTML 비교와 사용자 결정 필요 |
| AI 요청 경계·비용 차단·HTTP fake | 기능 기반 완료 | IMP-201~205C 완료, 실제 계정·과금 없음 |
| 실제 OpenAI 텍스트 보조 | POC 전 사용자 승인 게이트 | IMP-204C 소액 합성 계측과 IMP-205D Android 검증 대기 |
| 자유 음성 | 기기 비의존 POC 기반 완료 | IMP-301A 완료, 실제 마이크·권한·전사 IMP-301B 미구현 |
| 음성 핑퐁 | 요구사항·후속 계획 | 텍스트 MVP와 자유 음성 실기기 검증 뒤 진행 |

상태 이름은 서로 대신하지 않는다. HTML 목업 성공을 앱 구현 완료로, 자동 테스트 통과를 Android 검증으로, fake AI 성공을 실제 OpenAI 연결로 바꾸지 않는다.

## POC-first 실행 루프

1. 해결하려는 사용자 문제와 가장 큰 불확실성을 한 문장으로 적는다.
2. 실제 감정일기·비밀 키 없이 합성 데이터로 가장 작은 POC 또는 목업을 만든다.
3. POC가 증명할 수 있는 것과 증명할 수 없는 것을 먼저 적는다.
4. `docs/ui-qa-guide.md`의 해당 증거 층에서 검증한다.
5. 결과와 실패를 사용자에게 보여 주고 제품 방향 결정을 받는다.
6. 승인된 후보만 앱의 공통 계약과 세로 흐름에 통합한다.
7. 자동 검증·비관적 독립 검수·Android 실기기 검증을 거쳐 해당 단계만 완료로 바꾼다.
8. 실패하거나 가치가 약한 POC는 제품 코드에 억지로 합치지 않고 폐기·보류 이유를 기록한다.

## QA가 단계마다 답해야 하는 질문

| 단계 | QA의 핵심 질문 | 원본 문서 |
|---|---|---|
| POC | 의도한 가능성과 핵심 실패를 재현했는가 | 구현별 계약 테스트·`implementation-plan.md` |
| 프로토타입 | 설명 없이 구조를 이해하고 실제 행동을 시작하는가 | `ui-qa-guide.md` 사용자 첫 보기 QA |
| 기능 조각 | 정상·실패·취소에서 상태와 데이터가 보존되는가 | 테스트·`development-workflow.md` 독립 검수 |
| MVP | 같은 SHA가 Android에서 저장·재실행·수정·삭제까지 이어지는가 | `device-validation-checklist.md` |
| 외부 AI·음성 | 개인정보·삭제·비용·네트워크 실패 경계를 실제로 검증했는가 | IMP-204C·205D·301B와 관련 결정 |

QA는 POC를 제품처럼 보이게 만드는 절차가 아니라, **다음 단계로 승격해도 되는지를 반증하는 게이트**다. 확인된 오류가 있거나 사용자의 제품 결정이 남으면 다음 단계로 자동 승격하지 않는다.

## 현재 다음 행동

1. `docs/prototypes/emotion-map-ab-preview.html`에서 A안과 B안을 비교한다.
2. A/B의 첫 보기·320·360·412px QA 증거를 사용자에게 제시한다.
3. Q-034에서 시각 톤, Q-035에서 공간 탐색 구조를 사용자가 결정한다.
4. 승인된 UI만 앱에 통합하고 자동 검증·독립 검수를 수행한다.
5. 새 기준 SHA에서 IMP-106 Android 누적 검증을 재개한다.
6. 그 뒤 실제 OpenAI 조건·소액 계측 IMP-204C와 Android 통합 IMP-205D로 텍스트 MVP를 완료한다.
