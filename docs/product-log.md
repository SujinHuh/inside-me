# Inside Me 제품 대화 로그

이 문서는 제품 아이디어가 나온 원래 맥락을 잃지 않기 위한 추가 전용 로그다. `requirements.md`가 현재의 결론을 보여준다면, 이 문서는 사용자가 무엇을 말했고 AI가 어떻게 해석·제안했는지 시간순으로 보존한다.

## 기록 규칙

- 과거 항목은 삭제하거나 의미가 달라지게 고치지 않는다.
- 정정은 새 로그 항목을 추가하고 정정 대상 ID를 연결한다.
- 새 로그를 쓰기 전에 같은 날짜의 마지막 번호를 확인하고 다음 번호를 사용한다. ID를 중복하거나 재사용하지 않는다.
- 사용자 발화는 가능한 한 원문을 보존한다. 음성 인식으로 불명확한 표현은 원문에 그대로 두고 해석과 질문을 분리한다.
- AI의 해석을 사용자의 확정된 요구로 둔갑시키지 않는다.
- 실제 개인 감정일기, 인증정보와 불필요한 개인정보는 이 개발 로그에 넣지 않는다.
- `종류`와 `상태`는 아래 기본 값을 하나 이상 포함한 복수·설명형 표현을 허용한다. 여러 상태가 섞이면 무엇이 확정되고 무엇이 미결정인지 본문에서 구분한다.

```text

- 일시:
- 종류: 아이디어 | 요구사항 | 결정 | 정정 | 질문 | 참고자료 | 개발 지침 | 공식 문서 확인
- 관련 요구사항:
- 관련 결정:
- 상태: 포착 | 제안됨 | 임시 운영 | 확정 | 보류 | 거절 | 대체됨

### 사용자 원문

### 해석 및 구조화

### AI 제안 및 대안

### 트레이드오프
선택에 따른 이점, 비용, 위험과 포기하는 것을 기록한다.

### 미해결 질문
아직 결정되지 않은 내용을 기록한다.
```

## LOG-20260818-002 — 막연한 기분에서 세밀한 감정 찾기

### 해석 및 구조화

- 핵심 문제는 “기분이 나빴다”처럼 뭉뚱그린 상태를 서운함, 섭섭함, 우울함 등의 더 구체적인 감정으로 구분하기 어렵다는 것이다.
- 사용자가 자기 감정을 스스로 알아차릴 수 있게 돕는 것이 목적이다.
- 요구사항은 완성된 문장보다 러프한 대화로 수집하고 구조화한다.
- 솔로 풀스택 개발자가 직접 사용할 수 있는 작은 범위를 우선한다.
- AI 개발 지침을 `AGENTS.md`에 둔다.

### AI 제안 및 대안

- 상황 → 생각 → 몸의 반응 → 행동 충동 → 감정 후보 → 욕구 → 기록의 탐색 흐름을 제안했다.
- AI가 감정을 판정하지 않고 후보를 제안하며 사용자가 직접 선택하는 제품 원칙을 제안했다.
- 로그인, 소셜, 복잡한 통계 없이 대화형 감정 탐색과 기록부터 시작하는 MVP를 제안했다.

### 트레이드오프

- 질문이 많을수록 세밀한 탐색이 가능하지만 매일 쓰기 어려워질 수 있다.
- AI가 강하게 해석하면 빠르게 답을 얻는 느낌은 있지만 오판과 의존 위험이 커진다.
- 작은 MVP는 장기 통계와 확장 기능을 늦추지만 핵심 가치 검증 속도를 높인다.

### 미해결 질문

- 질문 수와 한 번의 권장 탐색 시간은 아직 정하지 않았다.
- 감정을 찾는 정확성과 사용 피로 사이의 균형을 도그푸딩으로 검증해야 한다.

### 해석 및 구조화

- 현재 요구사항만 남기는 것으로는 부족하며 아이디어의 원래 맥락과 변화 과정도 보존해야 한다.
- 사용자 발화, AI의 해석과 제안, 확정된 결정, 미결정 사항, 대안과 트레이드오프가 모두 추적되어야 한다.
- 이후 어떤 AI 에이전트가 개발하더라도 같은 로깅 규칙을 따라야 한다.

- 모든 AI 답변 전문까지 중복 저장하면 신호보다 잡음이 커질 수 있어, 사용자 제품 발화는 원문으로 보존하고 AI 답변은 제안·대안·트레이드오프 중심으로 구조화한다.
- 확정 요구와 제안을 분리하면 문서가 늘어나지만 AI 제안이 사용자 결정으로 오인되는 일을 줄인다.

### 미해결 질문

- AI 답변도 전문 그대로 보존할지, 현재 제안처럼 구조화된 요약만 보존할지 사용자의 확인이 필요하다.
- 로그가 커졌을 때 연도 또는 월 단위로 분할할지는 실제 크기를 본 뒤 결정한다.

## LOG-20260819-010 — 병렬 담당의 프론트엔드·백엔드 경계 질문

- 일시: 2026-08-19
- 종류: 구현 운영 논의, 역할 경계, 구현 계획 작성 전 확인

### 해석 및 구조화

- 앞서 제안한 주 담당자와 A·B·C 작업자가 프론트엔드, 백엔드 또는 둘을 합친 역할인지 명확한 설명을 요청했다.
- 사용자는 프론트엔드 작업자와 백엔드 작업자를 별도로 두는 전통적인 분업 방식도 적절하다고 보고 비교를 원한다.
- 역할 경계를 먼저 상의한 뒤 구현 계획을 확정해 작성하기를 원한다.
- 따라서 기존 DEC-034와 구현 계획의 병렬 운영안은 계속 `제안됨`으로 두며 이 턴에서 확정하지 않는다.

### 현재 제안의 의미

- 작업 A는 서버 백엔드가 아니라 앱 내부의 도메인 규칙과 기기 로컬 저장을 담당하므로 백엔드와 유사한 비화면 영역이다.
- 작업 B와 C는 화면과 사용자 상호작용 중심의 프론트엔드 작업이며, A가 제공하는 저장 인터페이스를 사용한다.
- 주 담당자는 Expo 기반, 공통 계약, 라우트 연결과 전체 통합을 맡는다.
- 첫 MVP는 기록을 기기에 저장하고 실제 AI 서버를 아직 연결하지 않으므로 독립된 서버 백엔드 작업이 없다.

### 논의할 대안

1. 기능 세로 흐름별로 프론트와 핵심 로직을 함께 맡기는 방식
2. 프론트엔드 담당과 서버 백엔드 담당을 완전히 분리하는 방식
3. 첫 로컬 MVP에서는 앱 UI, 앱 핵심·로컬 저장, 통합으로 나누고 실제 AI 연동 단계부터 프론트와 서버 백엔드를 분리하는 단계별 혼합 방식

### AI 권고

- 3번을 권고한다.
- 첫 로컬 MVP에는 서버를 억지로 만들지 않고 앱 UI 담당 둘, 앱 내부 핵심·저장 담당 하나와 주 통합 담당으로 구성한다.
- 실제 AI 비밀 키와 외부 전송이 필요한 2단계부터 서버 백엔드 담당을 별도로 두고, 프론트엔드 AI 경험 담당과 병렬로 작업한다.
- 이 권고는 사용자가 역할 구성을 확인한 뒤 DEC-034와 구현 계획에 확정 또는 수정 반영한다.

### 트레이드오프

- 처음부터 프론트와 서버를 분리하면 익숙한 역할 경계는 선명하지만 현재 필요하지 않은 API와 네트워크 실패 지점이 생긴다.
- 로컬 MVP를 기능별로 나누면 빠르게 전체 흐름을 검증할 수 있지만 작업 A를 전통적인 서버 백엔드로 오해할 수 있다.

- `app/index.tsx`를 feature 화면을 내보내는 한 줄 진입점으로 줄이고 실제 홈 화면을 `src/features/home/`으로 옮겼다.
- 저장소 테스트를 공통 합성 fixture, CRUD, 런타임 경계, 실패 주입으로 분리하고 증가형 ID factory, 월별 defensive copy와 실패 뒤 기록 보존 검증을 추가했다.

## LOG-20260820-010 — 기능 완료마다 push와 PR 생성·갱신을 지속 루프에 포함

- 일시: 2026-08-20
- 종류: Git·PR 운영 규칙 확정, 현재 기능 원격 게시
- 관련 요구사항: REQ-019, REQ-020, REQ-023
- 관련 결정: DEC-033, DEC-035, DEC-038, DEC-042
- 관련 질문: 없음
- 상태: 지속 루프 정책 커밋 `ac123c8` 독립 검수 완료, 상태 문서 커밋 뒤 현재 브랜치 push·PR 생성 대기

### 사용자 원문

> push 하면서pr 올리는거 알지?
>
> 이것도 각기능이 끝날때마다.
> docs에서 pr 템플릿 참고해서 작성해서 항상 같이 올리라고
> 루프돌리는 문서에 넣어줘

### 해석과 확정한 규칙

- 각 기능 단위가 자동 검증과 서브에이전트 독립 검수에서 확인된 오류 0개로 통과하면 구현·관련 문서를 기능 커밋 SHA A로 고정하고, 원장에 SHA A를 기록한 상태 문서 커밋 SHA B를 만든 뒤 clean 상태에서 현재 개발 브랜치를 push한다.
- 같은 head 브랜치의 PR을 먼저 확인하고, 없으면 `main` 대상으로 생성하며 이미 있으면 중복 생성하지 않고 제목·본문·Draft 상태를 갱신한다.
- PR 본문은 `.github/pull_request_template.md`와 `docs/pull-request-guide.md`를 기준으로 실제 변경 유형, 실행한 검증, 미검증 이유, 관련 REQ·DEC·LOG와 개인정보·로컬 데이터 영향을 매번 작성한다.
- `main...head` 전체 PR 범위의 모든 완료 기준·자동 검증·독립 검수가 통과하고 미완료 항목이 없을 때만 병합 가능한 PR로 표시하며, 하나라도 남으면 Draft를 유지한다.
- 이 지속 승인은 `inside-me`의 현재 기능 개발 브랜치 push와 PR 생성·갱신에만 적용한다. force push, PR 병합, 배포와 다른 저장소 원격 변경은 포함하지 않는다.

### 현재 실행

- `feat/expo-foundation`에는 동일 head 브랜치의 기존 PR이 없음을 확인했다.
- Git·PR 안전과 문서 정합성 독립 검수에서 확인된 오류를 모두 수정하고 최종 오류 0개를 확인해 정책 커밋 `ac123c8`로 고정했다.
- 이 SHA를 기록한 상태 문서 커밋을 만든 뒤 root·origin·브랜치·최신 main·전체 게시 범위·민감정보를 재확인하고, 브랜치를 origin에 non-force push해 템플릿에 맞는 새 PR을 생성한다.
