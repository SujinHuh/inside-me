# Inside Me PR 작성 가이드

## 목적

모든 PR에서 변경 내용뿐 아니라 변경 이유, 검증 결과, 제품 문서 연결과 개인정보 영향을 같은 형식으로 확인한다. GitHub PR 작성 화면에서는 [공통 PR 템플릿](../.github/pull_request_template.md)이 자동으로 열린다.

## 작성 원칙

1. 실제 변경에 해당하는 유형만 선택한다. 예를 들어 문서만 바꾼 PR에서 `신규 기능 추가`나 `코드 리팩터링`을 선택하지 않는다.
2. 변경 내용 요약에는 파일 이름만 나열하지 않고 사용자가 겪는 동작 또는 문서에서 달라진 기준을 적는다.
3. 변경 이유에는 해결하려는 문제와 지금 이 작업이 필요한 이유를 적는다.
4. 실행한 검증만 체크한다. 실행하지 못한 테스트, 타입 검사, 린트와 빌드는 빈 체크 상태로 두고 이유를 적는다.
5. 제품 동작이나 결정에 영향을 주면 관련 `REQ-*`, `DEC-*`, `LOG-*`를 연결한다. 관련 항목이 없으면 `없음`이라고 명시한다.
6. 실제 감정일기, 음성, 전사, API 키와 인증정보가 포함되지 않았는지 확인한다.
7. 로컬 기록 형식이나 저장 동작을 바꾸면 호환성과 마이그레이션 영향을 적는다.
8. 아직 검토가 필요한 작업은 Draft로, 완료 기준과 검증을 충족한 작업은 병합 가능한 PR로 표시한다.

## 섹션별 작성 방법

### 변경 유형

이번 PR의 성격을 빠르게 구분한다. 여러 유형에 해당하면 복수로 선택할 수 있다.

### 변경 내용 요약

리뷰어가 diff를 열기 전에 바뀐 범위를 이해할 수 있도록 핵심 변경을 3~5개 안팎으로 적는다.

### 변경 이유

구현 방법보다 사용자 문제, 제품 목표와 기술적 필요를 중심으로 적는다.

### 테스트 및 검증

명령 이름과 결과를 적고, 실제 기기나 화면에서 확인했다면 사용한 환경도 적는다. 문서만 변경한 경우에는 Markdown 공백 검사, 링크 확인과 비밀정보 검수처럼 실제로 수행한 검증을 적을 수 있다.

### 연관 문서 및 이슈

제품 요구사항, 결정과 대화 로그를 연결해 변경의 근거를 추적할 수 있게 한다. GitHub 이슈가 없다면 새 이슈를 억지로 만들지 않는다.

### 개인정보·보안·데이터 영향

민감정보 전송, 비밀정보, 로컬 기록의 호환성과 마이그레이션 영향을 각각 확인한다. 영향이 없다면 `없음`이라고 명시한다.

### 추가 설명과 남은 위험

의도적으로 제외한 범위, 후속 작업, 알려진 한계와 되돌리거나 재검토할 조건을 적는다.

### 리뷰 요청

Draft 여부를 표시하고 디자인, 데이터 구조, 안전 문구 등 특별히 확인받고 싶은 부분을 구체적으로 적는다.
