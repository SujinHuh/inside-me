# Inside Me PR 작성 가이드

## 목적

모든 PR에서 변경 내용뿐 아니라 변경 이유, 검증 결과, 제품 문서 연결과 개인정보 영향을 같은 형식으로 확인한다. GitHub PR 작성 화면에서는 [공통 PR 템플릿](../.github/pull_request_template.md)이 자동으로 열린다.

## 작성 원칙

1. PR 제목은 `영어 type: 한국어 제목` 형식으로 작성한다. type은 아래 8개 중 주된 변경 목적 하나만 소문자로 선택하고 scope는 사용하지 않는다. 본문은 한국어로 작성하며 코드 식별자, 명령과 파일명은 원문을 유지할 수 있다.
2. 실제 변경에 해당하는 유형만 선택한다. 예를 들어 문서만 바꾼 PR에서 `신규 기능 추가`나 `코드 리팩터링`을 선택하지 않는다.
3. 변경 내용 요약에는 파일 이름만 나열하지 않고 사용자가 겪는 동작 또는 문서에서 달라진 기준을 적는다.
4. 변경 이유에는 해결하려는 문제와 지금 이 작업이 필요한 이유를 적는다.
5. 실행한 검증만 체크한다. 실행하지 못한 테스트, 타입 검사, 린트와 빌드는 빈 체크 상태로 두고 이유를 적는다.
6. 제품 동작이나 결정에 영향을 주면 관련 `REQ-*`, `DEC-*`, `LOG-*`를 연결한다. 관련 항목이 없으면 `없음`이라고 명시한다.
7. 실제 감정일기, 음성, 전사, API 키와 인증정보가 포함되지 않았는지 확인한다.
8. 로컬 기록 형식이나 저장 동작을 바꾸면 호환성과 마이그레이션 영향을 적는다.
9. 아직 검토가 필요한 작업은 Draft로, 완료 기준과 검증을 충족한 작업은 병합 가능한 PR로 표시한다.
10. 테스트 추가·수정에서 프로덕션 파일도 바뀌면 실제 결함, 승인된 동작 변경, 동작 보존 리팩터링 중 변경 근거를 밝힌다. 실패한 테스트를 통과시키기 위한 근거 없는 핵심 공개 동작 assertion 약화·snapshot 갱신·skip·테스트 전용 프로덕션 분기가 없는지 확인한다. 테스트 결함으로 구현 세부 assertion을 교체했다면 그 분류와 근거를 적는다.

## PR 제목 type

| type | 사용하는 경우 | 제목 예시 |
|---|---|---|
| `feat` | 새로운 사용자 기능이나 동작 추가 | `feat: 감정 직접 추가 기능 구현` |
| `fix` | 잘못된 동작이나 오류 수정 | `fix: 같은 날짜 기록 중복 저장 수정` |
| `refactor` | 동작을 바꾸지 않는 코드 구조 개선 | `refactor: 감정 탐색 서비스 책임 분리` |
| `test` | 테스트 추가·수정이 주된 목적 | `test: AI 비용 경계 회귀 테스트 보강` |
| `docs` | 문서만 변경 | `docs: 실기기 통합 검증 기준 정리` |
| `build` | 빌드 설정·패키지·의존성 변경 | `build: Expo SDK 호환 버전 갱신` |
| `ci` | GitHub Actions 등 CI 자동화 변경 | `ci: PR 자동 검증 워크플로 추가` |
| `chore` | 위 유형에 속하지 않는 저장소 유지보수 | `chore: 개발 도구 설정 정리` |

- 제목에는 type을 정확히 하나만 사용한다. 여러 변경이 함께 있으면 PR의 결과와 리뷰 초점을 가장 잘 설명하는 주된 목적을 고른다.
- `feature:` 대신 Conventional Commits에서 사용하는 `feat:`를 쓴다.
- `feat(emotion):` 같은 scope는 현재 사용하지 않는다. 모듈 수가 늘어 제목만으로 영역을 구분하기 어려워지면 재검토한다.
- `Draft`는 type이 아니다. 작업 중 PR은 GitHub Draft 상태로 만들고, 준비가 끝나면 Ready for review로 전환한다. `draft:` 또는 `[Draft]`를 제목에 붙이지 않는다.
- `feat!:`와 `BREAKING CHANGE`는 현재 개인 로컬 MVP의 기본 제목 유형에 포함하지 않는다. 공개 API·데이터 호환성 자동화가 필요해지면 별도 결정한다.

이 형식은 Conventional Commits의 `<type>: <description>` 구조를 PR 제목에도 적용한 저장소 규칙이다. 규격 자체는 커밋 메시지를 대상으로 하므로, PR 제목 자동 검사는 별도 CI를 도입하기 전까지 작성·검수 규칙으로 운영한다.

근거:

- [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)
- [GitHub Draft pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests#draft-pull-requests)

## 섹션별 작성 방법

### 변경 유형

본문에서는 이번 PR에 포함된 변경 성격을 빠르게 구분한다. 제목 type은 하나만 고르지만 본문의 변경 유형은 실제 변경에 따라 복수로 선택할 수 있다.

### 변경 내용 요약

리뷰어가 diff를 열기 전에 바뀐 범위를 이해할 수 있도록 핵심 변경을 3~5개 안팎으로 적는다.

### 변경 이유

구현 방법보다 사용자 문제, 제품 목표와 기술적 필요를 중심으로 적는다.

### 테스트 및 검증

명령 이름과 결과를 적고, 실제 기기나 화면에서 확인했다면 사용한 환경도 적는다. 문서만 변경한 경우에는 Markdown 공백 검사, 링크 확인과 비밀정보 검수처럼 실제로 수행한 검증을 적을 수 있다.

테스트가 실패해 코드를 수정했다면 코드 결함·테스트 결함·환경 결함·요구사항 미결정 중 무엇이었는지와 근거를 적는다. `test` 중심 PR에 프로덕션 코드가 포함되면 변경 전 정상 동작을 보존했는지, 또는 어떤 확인된 오류·승인된 동작을 수정했는지와 회귀 검증을 명시한다.

### 연관 문서 및 이슈

제품 요구사항, 결정과 대화 로그를 연결해 변경의 근거를 추적할 수 있게 한다. GitHub 이슈가 없다면 새 이슈를 억지로 만들지 않는다.

### 개인정보·보안·데이터 영향

민감정보 전송, 비밀정보, 로컬 기록의 호환성과 마이그레이션 영향을 각각 확인한다. 영향이 없다면 `없음`이라고 명시한다.

### 추가 설명과 남은 위험

의도적으로 제외한 범위, 후속 작업, 알려진 한계와 되돌리거나 재검토할 조건을 적는다.

### 리뷰 요청

GitHub Draft 여부를 표시하고 디자인, 데이터 구조, 안전 문구 등 특별히 확인받고 싶은 부분을 구체적으로 적는다. Draft 상태를 제목 문자열로 중복 표시하지 않는다.
