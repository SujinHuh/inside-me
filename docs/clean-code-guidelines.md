# Inside Me 클린 코드 지침

- 작성일: 2026-08-20
- 상태: 현재 구현과 이후 개발에 적용
- 관련 결정: DEC-020, DEC-027, DEC-028, DEC-038, DEC-041, DEC-052
- 관련 로그: LOG-20260820-009, LOG-20260824-022, LOG-20260824-023

## 목적

이 문서는 클린 코드를 단순히 파일을 짧게 만들거나 이름을 예쁘게 짓는 규칙으로 다루지 않는다. Inside Me에서 클린 코드는 감정 기록을 잃거나 잘못 확정하지 않도록 책임과 데이터 경계를 분명히 하고, 다음 개발자가 코드 이름만 보고도 실제 보장 범위를 오해하지 않게 만드는 기준이다.

모든 구현은 `docs/development-workflow.md`의 실행·검수 절차와 이 문서를 함께 따른다. 취향에 따른 대규모 리팩터링보다 현재 사용자 흐름과 관련된 경계를 먼저 정리한다.

## 구현 전 확인

- 변경할 사용자 행동과 완료 조건을 먼저 확인한다.
- 기능 모듈, 핵심 규칙, 플랫폼 구현, 라우트와 테스트 중 어느 책임인지 정한다.
- 새 이름이 실제 책임보다 넓거나 좁지 않은지 확인한다.
- 저장·내보내기·외부 입력처럼 TypeScript 타입을 우회할 수 있는 경계인지 확인한다.
- 기존 계약을 바꾼다면 소비하는 화면·저장소·테스트와 마이그레이션 영향을 함께 확인한다.

## 계층과 의존성

- `src/core/`는 React Native, Expo Router, 운영체제 파일 API와 실제 저장 기술을 알지 않는다.
- `src/features/`는 사용자 행동과 화면 상태를 소유하고 core 계약과 application port를 사용한다.
- `src/platform/`과 `src/infrastructure/`는 바깥 기술을 구현하지만 core가 이 구현을 가져오지 않는다.
- `src/application/`은 사용자 행동 단위의 use case를 소유하고, `src/composition/`만 구체 adapter를 생성해 application port에 주입한다. 실제 앱이 `src/testing/` 구현을 가져오지 않는다.
- `app/`의 라우트 파일은 실제 화면을 다시 구현하지 않고 feature 화면을 내보내거나 의존성을 조합하는 얇은 진입점으로 유지한다.
- Expo Router가 `src/app/`을 라우트 루트로 해석할 수 있으므로 일반 조합 모듈에 `src/app/` 이름을 재사용하지 않는다.
- 아직 존재하지 않는 Expo Router 경로를 수동 라우트 목록에 미리 등록하지 않는다. 실제 파일 경로와 Expo typed route를 단일 원본으로 사용한다.

## 런타임 데이터 경계

- 외부 저장 데이터, JSON, 마이그레이션, JavaScript 호출과 테스트 cast는 TypeScript 타입을 우회할 수 있다고 가정한다.
- `validate*`라는 이름은 검사만 하는지, 안전한 값으로 변환해 반환하는지 이름과 반환 타입으로 구분한다.
- 저장 경계는 일부 필드만 확인한 원본 객체를 펼쳐 저장하지 않는다.
- parser는 모든 필수 필드와 판별값을 검사하고 성공하면 허용된 필드만 새 객체로 투영한다. 알 수 없는 추가 필드는 저장·내보내기에 남기지 않는다.
- 사용자 표현은 임의로 다듬거나 교정하지 않고 유효성만 확인해 그대로 보존한다.
- 실제 저장 어댑터와 seed·migration 입력에도 같은 schema parser 또는 동일한 계약 테스트를 적용한다.

## 이름과 타입

- 이름은 실제 책임 전체를 표현한다. 감정과 욕구를 모두 다루는 계약을 감정 전용처럼 이름 짓지 않는다.
- `unknown`, `confirmed`처럼 동시에 존재할 수 없는 상태는 판별 유니언으로 표현한다.
- 날짜와 월처럼 오류 의미가 다른 parser는 각 결과 타입의 오류 범위를 좁힌다.
- 강제 단언과 `as unknown as`는 런타임 경계 테스트처럼 의도가 분명한 곳에만 사용한다.
- 오류 코드와 사용자 문구의 책임을 구분한다. 저장 계약은 안정적인 오류 의미를 제공하고, 실제 화면 문구는 presenter 또는 feature 계층에서 관리하는 방향으로 발전시킨다.

## 복사와 데이터 보존

- JSON 직렬화를 단순 복사 도구로 사용하지 않는다. 필드 추가 시 값이 조용히 사라질 수 있다.
- 복사가 필요한 경계는 이름이 있는 clone 함수와 `structuredClone` 또는 명시적 mapper를 사용한다.
- 저장 입력, 저장 반환값, 단건 조회, 월별 목록, 전체 목록과 seed가 내부 상태를 참조로 노출하지 않는지 테스트한다.
- 실패·삭제·갱신 테스트는 성공 여부만 보지 않고 이전 기록이 유지되거나 의도대로 없어졌는지 확인한다.

## 테스트 구조

- fixture 생성, 정상 CRUD, 런타임 경계 검증과 실패 주입을 한 테스트 파일에 계속 누적하지 않는다.
- 합성 fixture builder와 결과 narrowing helper를 공통으로 사용해 실패 원인이 분명하게 보이게 한다.
- ID·시간·날짜 factory는 결정적이어야 하며, 서로 다른 새 기록에 같은 ID를 반환하는 비현실적인 기본값을 사용하지 않는다.
- fake 전용 테스트에 그치지 않고 실제 SQLite 같은 어댑터에도 재사용할 repository contract test를 만든다.
- 실제 일기·전사·개인정보는 fixture, snapshot과 오류 메시지에 넣지 않는다.

## 테스트 무결성과 기존 동작 보호

### 무엇을 보호하는가

- 테스트의 목적은 테스트 자체를 통과시키는 것이 아니라 요구사항과 사용자가 관찰하는 공개 동작, 데이터 보존 계약을 검증하는 것이다.
- 기존에 정상이라고 합의되고 검증된 사용자 동작은 새 테스트의 예상값에 맞추기 위해 임의로 바꾸지 않는다.
- 테스트는 공개 API와 결과를 우선 확인한다. 내부 함수 호출 횟수·배열 순서·구현 클래스처럼 요구사항이 아닌 세부 사항은 성능, 단일 요청, 보안처럼 명시된 비기능 계약을 검증할 때만 고정한다.
- 테스트 추가·수정 작업을 시작하기 전에 가능한 관련 기존 테스트를 실행해 기준선을 기록한다. 이미 실패하던 항목은 새 변경 때문에 생긴 실패처럼 보고하지 않는다.

### 실패 원인 분류

새 테스트나 기존 회귀 테스트가 실패하면 다음 순서로 판단한다.

1. 관련 `REQ-*`, `DEC-*`, 사용자 행동과 기존 공개 계약에서 기대 결과의 근거를 확인한다.
2. 같은 테스트를 격리 실행해 재현하고 입력, mock·fake, 시간·날짜, 비동기 대기와 테스트 정리 상태를 확인한다.
3. 실패 원인을 `프로덕션 코드 결함`, `테스트 결함`, `환경·도구 결함`, `요구사항 미결정` 중 하나로 분류한다. 근거가 부족하면 코드를 고치지 않고 미결정 또는 차단으로 기록한다.
4. 코드 결함이면 사용자 동작을 바로잡고 회귀 테스트를 유지한다. 테스트 결함이면 프로덕션 동작을 바꾸지 않고 fixture·예상값·대기·격리를 수정한다. 환경 결함이면 설정과 재현 조건을 고치되 검증 수준을 낮추지 않는다.
5. 수정 뒤 표적 테스트와 영향받는 전체 검증을 다시 실행하고, 독립 검수자에게 실패 분류와 실제 변경 근거를 전달한다.

### 프로덕션 코드 변경 허용 범위

테스트 작성 과정에서 프로덕션 코드 변경은 다음 세 경우에만 허용한다.

- 요구사항과 재현 근거로 확인된 실제 동작 오류·데이터 안전 결함을 수정한다.
- 사용자가 승인한 신규 또는 변경 동작을 TDD 방식으로 구현한다.
- 공개 동작과 데이터 형식을 유지하면서 의존성 주입, 경계 분리처럼 테스트 가능성을 개선한다.

`test`가 주목적인 작업에서 프로덕션 파일이 바뀌면 PR에 위 분류, 사용자 동작 영향, 변경하지 않은 계약과 실행한 회귀 검증을 적는다. 동작 보존 리팩터링이라고 설명했다면 기존 공개 동작 테스트가 수정 전·후 같은 기대값으로 통과해야 한다.

### 금지하는 통과 방식

- 요구사항 근거 없이 핵심 공개 동작 assertion을 약화하거나 예상값을 삭제하지 않는다. 테스트 결함으로 구현 세부 assertion을 교체한다면 실패 분류와 근거를 남긴다.
- 근거 없이 snapshot을 일괄 갱신하거나 테스트를 `skip`, `only`, 주석 처리하지 않는다.
- 비동기 실패를 감추기 위해 임의의 긴 sleep·timeout을 추가하지 않는다. 완료 신호나 제어 가능한 clock·deferred promise를 사용한다.
- 테스트에서만 실행되는 조건문, 비공개 상태 노출용 export와 실제 사용자에게 불필요한 우회 경로를 프로덕션 코드에 추가하지 않는다.
- mock이 원하는 값을 반환하도록 프로덕션 입력을 왜곡하거나, 실제 adapter와 다른 계약을 fake에만 구현하지 않는다.
- 단순히 모든 테스트가 초록색이라는 이유로 사용자 동작, 데이터 보존과 테스트 유효성 검수를 생략하지 않는다.

### 격리와 복원

- 단위 테스트는 빠르고 독립적이며 같은 입력에서 반복 가능한 결과를 내야 한다.
- 파일, SQLite, 네트워크, 시간과 운영체제 API는 테스트 목적에 따라 fake·mock·임시 namespace로 격리하고 실제 앱 데이터와 외부 서비스에 접근하지 않는다.
- mock, spy, timer, 임시 파일과 DB는 테스트 뒤 복원·정리한다. 한 테스트의 상태가 실행 순서에 따라 다른 테스트 결과를 바꾸면 완료로 처리하지 않는다.

## 구현 완료 전 체크리스트

- [ ] 파일과 함수 이름이 실제 책임과 보장 범위를 설명한다.
- [ ] core가 feature·platform·infrastructure 구현을 역으로 참조하지 않는다.
- [ ] `app/` 라우트가 얇고 실제 Expo Router 경로와 계약이 일치한다.
- [ ] 타입을 우회한 잘못된 입력과 알 수 없는 추가 필드를 검사했다.
- [ ] parser 성공값은 허용 필드만 포함한다.
- [ ] 정상·실패·데이터 보존·참조 복사 테스트가 있다.
- [ ] 테스트 fixture의 ID와 시간이 실제 규칙을 왜곡하지 않는다.
- [ ] 테스트가 공개 동작·안정된 계약을 검증하고 요구사항이 아닌 구현 세부에 과결합하지 않는다.
- [ ] 실패 원인을 코드·테스트·환경·미결정으로 분류했고 정상 동작을 잘못된 테스트에 맞춰 바꾸지 않았다.
- [ ] 근거 없이 핵심 공개 동작 assertion을 약화하거나 snapshot 갱신·skip·테스트 전용 프로덕션 분기로 실패를 숨기지 않았다. 테스트 결함으로 assertion을 교체했다면 분류와 근거를 기록했다.
- [ ] 프로덕션 코드를 바꿨다면 실제 결함·승인된 동작·동작 보존 리팩터링 중 근거와 회귀 영향을 기록했다.
- [ ] mock·spy·timer·임시 파일·DB를 격리하고 복원해 테스트 순서가 결과를 바꾸지 않는다.
- [ ] 테스트, 타입 검사, 린트와 관련 빌드를 실행했다.
- [ ] 서브에이전트 독립 검수에서 클린 코드와 계층 방향을 확인했다.
- [ ] 남은 리팩터링을 오류와 후속 제안으로 구분해 구현 상태 원장에 기록했다.
